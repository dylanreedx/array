# P5.2 — Integrate capability-driven ready, working, stop, steer, and failure states

Phase: 5 · Live integration
Execution: **autonomous**
Depends on: P5.1

## Goal

Give the live tile truthful operational states without tying UI semantics to provider process liveness.

## Context and design direction

Read `_DESIGN.md` and `_RUNBOOK.md` before editing. The semantic document—not a view and not a
Markdown-library AST—is the source of truth. Preserve the agent/tile ownership split, light/dark
tokens, keyboard accessibility, and I5. Visible Aqua dropdown or rounded text-field styling is not
acceptable in new tile UI. This ticket is deliberately scoped so another fresh agent can verify and
commit it independently.

## Approach

1. Derive ready/working/queued/needs-action/failed/restored from supervisor turn facts and runtime capabilities. `needs-action` must identify the explicit unresolved provider request that the live tile can reveal; a status chip with no route to request context/actions is incomplete.
2. Route Send and Stop through one `AgentTileActionSink`; adapt current supervisor conservatively.
3. When RPC capabilities later expose steer/queue, the presenter changes state without replacing the composer.
4. Consume any provider response-mode capability that Queue 90/runtime has already compiled into the provider-neutral seam (fixed-choice, freeform, optional-note): surface it as factual state the composer variants can key on. `AgentRequestPayload` currently carries only requestID/prompt/status/choices — if no compiled response-mode capability exists, requests remain fixed-choice; never infer a freeform or note mode from empty choices, and do not add runtime/RPC behavior in Queue 91 to create one.
5. Preserve draft until an intent is accepted.

### Implementation sketch

```swift
protocol AgentTileActionSink: AnyObject {
    func accept(_ intent: AgentComposerIntent, for agentID: AgentID) async -> IntentAcceptance
}
```

The sketch establishes ownership and direction; adapt names to the compiled code, but do not replace
the architecture with a shortcut that couples parsing, rendering, and agent execution.

### State provenance

Every visible operational state comes from explicit supervisor turn facts, provider-enforced needs, and compiled capabilities. Never infer working, queued, approval-needed, or plan progress from process liveness, elapsed time, tool names, or assistant prose. Missing capability means unavailable, not optimistic UI.

## Done when

- Every state exposes truthful action and accessibility description.
- Needs-action navigation reveals the matching request context and available provider choices rather than a generic attention label or permanent dock.
- A refused send/stop keeps UI/draft consistent.
- Process alive but idle presents Ready, not Working.
- Relevant new behavior has a deterministic positive assertion and at least one required negative
  witness observed red against the final check.
- No existing matrix leg, assertion floor, contrast requirement, or I5 boundary is weakened.
