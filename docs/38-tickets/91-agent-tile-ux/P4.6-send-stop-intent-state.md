# P4.6 — Model composer actions as intents and capabilities

Phase: 4 · Composer
Execution: **autonomous**
Depends on: P4.5

## Goal

Prevent the composer from hard-coding today’s disabled-while-working behavior and make Send/Stop/Steer/Queue extensible.

## Context and design direction

Read `_DESIGN.md` and `_RUNBOOK.md` before editing. The semantic document—not a view and not a

## Approach

1. Define intents separately from presentation and runtime execution.
2. Derive one primary action and allowed secondary behavior from explicit capabilities/state.
3. Build a custom icon/text action button with loading/disabled/focus states.
4. Keep current runtime mapping conservative: if steer/queue is unavailable, do not imply it works.

### Implementation sketch

```swift
enum AgentComposerIntent { case send(String), stop, steer(String), queue(String), command(String) }
struct AgentTurnCapabilities { var canSend: Bool; var canStop: Bool; var canSteer: Bool; var canQueue: Bool }
```

The sketch establishes ownership and direction; adapt names to the compiled code, but do not replace
the architecture with a shortcut that couples parsing, rendering, and agent execution.

### Compiled-capability floor

Send and Stop are advertised only when the current supervisor/runtime can execute them. Steer and Queue remain typed future intents but must be unavailable and visually unclaimed until an explicit queue-90 capability reaches the provider-neutral seam. Never simulate them by dropping or replaying prompts.

## Done when

- Every state/capability combination has exactly one truthful primary action.
- Working without RPC never shows a fake steer action.
- Relevant new behavior has a deterministic positive assertion and at least one required negative
  witness observed red against the final check.
- No existing matrix leg, assertion floor, contrast requirement, or I5 boundary is weakened.
