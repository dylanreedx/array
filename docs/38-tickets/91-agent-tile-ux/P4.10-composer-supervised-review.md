# P4.10 — Supervised composer design review

Phase: 4 · Composer
Execution: **supervised**
Depends on: P4.9

## Goal

Review the complete isolated composer—editing, growth, custom choices, action states, and completion popup—before integrating it into the live tile.

## Context and design direction

Read `_DESIGN.md` and `_RUNBOOK.md` before editing. The semantic document—not a view and not a
Markdown-library AST—is the source of truth. Preserve the agent/tile ownership split, light/dark
tokens, keyboard accessibility, and I5. Visible Aqua dropdown or rounded text-field styling is not
acceptable in new tile UI. This ticket is deliberately scoped so another fresh agent can verify and
commit it independently.

## Approach

1. Apply the recorded owner dropdown corrections (below) to `ChoiceButton` and `ChoiceListView`.
2. Render empty, focused, multiline, long, working/Stop, narrow, model menu, effort menu, and completion states in both themes, plus the two composer variant review states (below).
3. Exercise real typing, IME/marked text, undo, history, selection, and keyboard navigation in an installed candidate.
4. Ask the owner whether the editor and choice controls feel friendly and intentionally Continuum—rather than a form field, stock dropdown, or raw de-Aqua imitation—and whether focus/selection is immediately visible.
5. Bless only approved candidate baselines and record corrections.

### Owner dropdown corrections (2026-07-31 review — current design not approved)

- `ChoiceButton` idle state uses a quiet fill with no heavy idle outline; any boundary it keeps is
  at most 0.5 pt.
- Remove permanent grey borders around individual options: `ChoiceRowView` must not paint a
  perimeter border for focus or selection.
- Reduce row height from 44 pt toward approximately 34–36 pt.
- The choice panel keeps exactly one subtle boundary; no nested boxes (panel border plus row
  borders).
- Communicate states through: selected fill plus checkmark; soft hover fill; a temporary
  keyboard-focus treatment (accent, fill, glow, or another non-permanent cue — never a thick grey
  border); muted text plus accessibility semantics for disabled items.
- Keyboard focus must remain immediately visible and accessible in both themes; no existing focus,
  contrast, or accessibility assertion may be weakened to satisfy the density corrections.
- The owner's global "all app borders ≤ 0.5 pt" requirement is broader than this fence and is
  owned by `docs/38-tickets/93-global-border-audit.md`. This packet corrects only the choice
  family named in its fence; do not sweep other components here.

### Composer variant review states (owner-approved direction)

Add both states to Component Lab and review them in both themes:

1. **Full-turn composer** (existing production configuration): 1–8 visual lines, AgentID
   draft/history, model/effort controls, Send/Stop, provider-enabled `/`, `@`, and `$` completions.
2. **Compact freeform shell** (presentation-only): shared `ComposerTextView` behavior, 1–4-line
   shell, no model or effort controls, completions limited to references (`@` and `$`).
   `AgentRequestPayload` exposes no freeform or optional-note response contract, so this state is
   a visual/behavioral shell only: no RequestID draft keying, no send path, and no response mode
   inferred from empty choices. Queue 90/runtime must expose a provider-neutral response mode
   before later tickets make this variant actionable.

Fixed-choice approval/question surfaces keep provider choices as buttons — do not fabricate a text
editor for them. The optional-note reveal ("Write a note…") exists only when a provider explicitly
permits a note and is out of scope until that contract exists.
