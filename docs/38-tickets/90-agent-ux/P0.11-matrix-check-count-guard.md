# P0.11 — Guard: the matrix may never lose a check
Phase: 0 · Depends on: none · Tag: autonomous · Execution-mode: low

## Goal
The program's central rule is "never weaken the matrix," but nothing enforces it. An unattended
worker under pressure can delete or comment out a check to get green. Make that structurally
impossible to do quietly.

## Files
- `scripts/check-matrix-inventory.sh` (new)
- `docs/38-tickets/90-agent-ux/matrix-inventory.txt` (new, committed)
- `scripts/run-matrix.sh` (invoke the guard as a leg)

## Approach
Extract the sorted list of every `--*-check` flag and every `run `/`run_app_check` leg from
`run-matrix.sh`, plus the count of `run*Checks()` calls in the `*Checks` mains. Compare to the
committed inventory. **Fail if any entry disappeared or a count decreased**; pass (and print) when
entries are added. Growing the inventory is an explicit committed diff:
`CONTINUUM_UPDATE_MATRIX_INVENTORY=1 ./scripts/run-matrix.sh`.

## Done when
Deleting any check flag from `run-matrix.sh` turns the matrix red with a message naming the missing
check.

## Verify
`./scripts/run-matrix.sh` green. Then delete one `--*-check` line → red, message names it → restore.
Add a new check → the guard prints "inventory grew" and passes; regenerate the file and commit.

## Watch out
- Renames look like a deletion + an addition. That is correct behaviour — the human blesses it by
  regenerating the inventory in the same commit as the rename.
- P0.7 legitimately supersedes two ad-hoc delta assertions inside ComponentLab (not matrix legs), so
  the leg inventory must not shrink there either. If it would, the guard is right and P0.7 is wrong.
- Do not let the guard itself be the thing that gets disabled: it is a normal leg, so its absence
  trips the inventory too.
