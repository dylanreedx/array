# P3.15 — Wire the destructive row actions (an agent you cannot delete)

Phase: 3 · Depends: P3.12, P2A.7, P4.1

**PULLED FORWARD OUT OF PHASE ORDER, and it is a PLAN HOLE, not a missing phase.** The owner hit
this in the built app on 2026-07-26:

> "there is a lot of stale agents i cant delete..."

They are right and there is no workaround in the UI. This is the highest-priority ticket in the
queue when it is picked up.

## What is actually broken

`P2A.7` landed restore-on-relaunch, so every `AgentRecord` on disk comes back on every launch.
Nothing was ever wired to remove one. Confirmed on the owner's machine: three records in
`~/Library/Application Support/continuum-revived/agents/` from a scratch verification run
(`cwd` pointing at a `postfix-verify` scratch directory), resurrected on every launch, with no way
to dismiss them.

The capability exists and is good. **`AgentSupervisor.archive(_ id:) -> ArchiveReport`** (~line 813)
already does the whole job, in an order its own comments call load-bearing: it stops a live runner
first (because `stop` delivers a persist-worthy `.sessionStateChanged(.stopped)`, so stopping *after*
the delete writes the record straight back), then deletes the durable record BEFORE touching the
worktree (removing a worktree while the record survives leaves the next launch restoring an agent
whose checkout is gone), and it RETAINS an unmerged branch or a dirty worktree rather than force-
removing it, reporting that in `ArchiveReport`. `AgentStore.delete(id:)` (~line 131) is underneath it.

**Nothing calls it.** The gap is purely the wiring:

- `AgentInboxView` declares ten `InboxRowAction`s. Exactly one — `.openInTile` — is wired, via
  `onRevealRow`. The other nine are gated on `onRowAction != nil` (`isWired(_:)` ~line 1187).
- `AgentInboxView` declares five `InboxBulkAction`s, gated on `onBulkAction != nil` (~line 1094).
- **Neither callback is assigned anywhere in the shipped app.** The only assignments in the repo are
  in check code (`ContinuumApp.swift` ~22013 and ~22337) and a no-op Lab stub
  (`ComponentLab.swift:1547`). So the row menu shows nine greyed items and the bulk bar's menu never
  appears at all.

No packet in the queue was going to fix this. `P4.10-post-action-advance` (row 74) *presumes* actions
perform and only governs what the selection does afterwards. That is my planning error.

## MEASURED ON THE OWNER'S MACHINE: deleting the record is NOT deleting the agent

Do not start from the assumption that `archive` alone finishes the job. I removed all three records
from `agents/` with the app quit, relaunched, and **three records came straight back — same
`tileId`s, brand-new `AgentID`s.** The record is DERIVED state:

- The tiles are persisted per project, in `<projectRoot>/.continuum-revived/canvas.json`, alongside
  `managed-sessions/<tileId>.json` (ticket 88.5's `ManagedAgentSessionRecord`, which `P2A.1`
  deliberately left coexisting).
- At launch the app opens each registered project, restores its canvas, and each `managedAgent` tile
  wires up through the supervisor — which spawns and persists a NEW agent when it cannot find one for
  that tile. `P2A.3`'s note already says `agent(forTile:)` "dedupes within a session only".

So a Delete that only calls `archive` makes the row disappear and the agent **reappear on the next
launch under a new id** — which is worse than the current state, because it looks like it worked.
This ticket is not done until a deleted agent stays deleted across a relaunch, which is why that is
the last item in `## Verify`.

What to do about the tile is a real decision and the packet does not pretend otherwise. Deleting an
agent whose tile still exists must either delete the tile too, or mark the tile so wire-up does not
mint a replacement. **`P2A.4`/`P2A.5` established that closing a tile is a `detach()`, not a kill —
so the inverse must also hold: deleting an agent must not silently destroy a tile the user can see.**
If you cannot satisfy both without inventing policy, implement the honest subset (the agent stops and
its record goes), state the resurrection case explicitly in the ledger, and leave the tile question
for the owner. Do NOT quietly delete canvas tiles as a side effect of an inbox action.

## Why this is not just "assign the callback"

`isWired(_:)` returns `onRowAction != nil` for **all nine** actions as one group. Assigning the
callback therefore un-greys all nine at once — including two that have nowhere to go:

| Action | Destination today | Status |
|---|---|---|
| `.archive`, `.delete` | `AgentSupervisor.archive(_:)` | **exists** |
| `.stopAgent` | `AgentSupervisor.stop(_:)` | **exists** |
| `.settle`, `.unsettle` | `P4.1`'s `settledOverride`; `AgentSupervisor.clearSettle(agentID:)` | exists, but see scope |
| `.markUnread` | `P3.3` read-state | exists, but see scope |
| `.rename` | `AgentRecord.displayName` (`P3.13`: the name lives on the record) | exists, but see scope |
| `.snooze`, `.wake` | **nothing writes `snoozedUntil`** — `P4.5` built the presets and deliberately stopped there; `P4.6`/`P4.7` own the write and the shelf | **NO DESTINATION** |

So a blanket assignment produces two menu items that look live and do nothing. `P3.11` already made
exactly this call for the bulk bar and its reasoning holds here: with `onBulkAction` unset the menu
does not appear at all, *because* "the shipped sidebar would otherwise offer five silent no-ops".

**The fix is to make `isWired` per-action instead of one group.** That is the real change in this
ticket; the callback assignment is the easy half.

## Scope — deliberately narrow

**IN:** the per-action wiring gate, and `.delete` / `.archive` / `.stopAgent` reaching the supervisor
for both the row menu and the bulk bar. That is what unblocks the owner.

**OUT, and must stay greyed by the new gate rather than half-wired:** `.snooze` and `.wake` (no
destination until `P4.6`/`P4.7`). **ALSO OUT of this ticket, though they have destinations:**
`.settle`, `.unsettle`, `.markUnread`, `.rename` — wiring seven actions at once makes one commit that
touches read-state, lifecycle override and rename all together, and none of those is what the owner
is blocked on. They are a follow-up (`P3.16`), and the per-action gate this ticket builds is what
makes adding them a one-line change each.

Do not widen this. A stale agent the owner cannot remove is the bug.

## Approach

1. **Per-action capability, not one boolean.** Replace the grouped `case` in `isWired(_:)` with a
   per-action test. The honest form is a capability set or a per-action closure — an action is wired
   when there is something to run, not when *some* callback exists. `.snooze`/`.wake` must come out of
   this as **not wired** and therefore greyed, with the owning ticket named in a comment so the next
   worker sees why.

2. **Same for the bulk bar.** `InboxBulkAction.available(...)` already ANDs across selected members
   (`P3.11`: a running member removes Archive and Delete). Keep that intersection exactly as it is
   and add the capability test on top — an action must be both available for the selection AND wired.
   `P3.11`'s rule that an unavailable action is HIDDEN rather than greyed stays.

3. **Route delete and archive to `AgentSupervisor.archive`.** One destination for both verbs.
   `.delete` and `.archive` differ in what the user is told, not in what the app does — `P4.1` owns
   the `archived` lifecycle state, and this method is, in its own words, "only the cleanup the
   archive/delete action performs". If you conclude the two verbs must diverge, **say so and stop**;
   do not invent a second deletion path.

4. **Confirm it, and surface `ArchiveReport`.** This stops a running process and deletes durable
   state. Reuse the confirmation seam `P3.14` reported already sitting in front of workspace delete
   (`workspaceRenamePromptProvider` and its sibling) rather than inventing a second dialog style.
   **`ArchiveReport` is not decoration:** it reports a retained unmerged branch and a retained dirty
   worktree. Discarding that report means telling the user "deleted" while a branch with their
   commits survives. `P3.11` hit the same class of over-claim — its caption said "Keeps ⎇ …" when the
   row could not know merge state, and was corrected to `Unmerged work kept: ⎇ …`. Report what
   actually happened.

5. **`TRAP, measured by `P3.14`:** a prompt provider that returns `nil` does NOT decline — it falls
   through to the real `NSAlert.runModal` and **hangs a headless run**. `P3.14` sampled the wedged
   process. Whatever confirmation seam you use, the check must exercise a path that cannot reach a
   modal, and a cancelled action is the safer probe than a nil provider.

6. **A deletion must leave nothing behind.** After it, the record is gone from
   `AgentStore.layout.agentsDirectory`, the row is gone from the inbox, any runner is stopped, and a
   relaunch does not bring it back. That last clause is the whole point of the ticket — assert it by
   re-reading from disk, not from memory.

## Done when

- Right-clicking an agent row offers **Delete** and **Archive** live, and they work.
- Deleting removes the record from disk; a relaunch does not resurrect it.
- Deleting a *running* agent stops it first and says what was kept (branch, dirty worktree).
- The bulk bar appears for a multi-selection and its Delete/Archive perform.
- `.snooze` and `.wake` are still greyed, with `P4.6`/`P4.7` named in a comment.
- The full matrix is green, no floor lowered, no check loosened.

## Watch out

- **Never force-remove an unmerged branch or a dirty worktree.** `archive` deliberately retains both.
  Deleting an agent must not silently discard commits — the comment in `archive` says discarding
  commits is worse than leaving a branch for a human, and that judgement stands.
- **Closing a tile is not deleting an agent.** `P2A.4`/`P2A.5` made tile close a `detach()`; the agent
  keeps running headless. Do not conflate the two, and do not "fix" stale rows by deleting tiles.
- **`deleteTile` already exists and is scanned for** (`AgentSupervisor.swift` ~4892). It is a different
  verb. Leave it alone.
- Reading is free (`P4.9`): opening the confirmation must not mark a row read.
- Do not touch the transcript views (`P6.0`) or the model/effort controls (`P6.1`).
