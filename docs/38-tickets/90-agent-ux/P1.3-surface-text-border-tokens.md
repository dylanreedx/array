# P1.3 — The token set: surfaces, text, borders
Phase: 1 · Depends on: P1.2 · Tag: autonomous · Execution-mode: high

## Goal
One named, contrast-tested palette to replace ~20 scattered literals. Today the "same" dark
background exists as three different values (desktop tile `0.08,0.10,0.13`, snapshot backing the
same, iOS `0.05,0.06,0.08`), so the two platforms literally do not match.

## Files
- `Sources/ContinuumRevivedAgentUI/DesignTokens.swift` (new)
- `Sources/ContinuumRevivedAgentUIChecks/DesignTokenChecks.swift` (new)

## Approach
Semantic names only — never color names. Minimum set, each a `TokenColor`:
- surfaces: `canvas`, `tileBody`, `tileChrome`, `panel`, `overlay`
- card fills: `cardMessage`, `cardUserMessage`, `cardTool`, `cardPlan`, `cardDiff`, `cardError`
- text: `textPrimary`, `textSecondary`, `textOnAccent`
- lines: `border`, `borderStrong`, `separator`
- accents: `accentWorking`, `accentApproval`, `accentInput`, `accentFailed`, `accentDone`

Dark values: start from the current literals **except** where the audit proved them broken — the
tile border must not stay `white 0.25` on `white 0.10` (1.68:1). Light values: design them
(do not invert dark); light surfaces should be near-white with dark text, and accents must keep
their hue identity across themes so a status reads the same everywhere.

Pair the semantics explicitly: each text token documents which surfaces it is legal on, so P1.6 can
gate real pairs rather than a cross-product.

## Done when
Every token exists with both theme values, and every documented text/surface pair clears AA in both
themes.

## Verify
`DesignTokenChecks`: totality (every token non-nil in both themes), documented-pair contrast
≥4.5 (text) / ≥3.0 (borders, accents-as-glyph), background distinctness by `hexKey`, and the
metric anchor (white/black ≈21:1) so the suite cannot pass vacuously. Add regression witnesses:
`white 0.25` on `white 0.10` must FAIL; `tertiaryLabel`-equivalent grey on `cardMessage` must FAIL.

## Watch out
- This is the ticket most likely to be "finished" with plausible-but-unchecked colors. Every value
  must be justified by a computed ratio, not by taste.
- Do not adopt tokens into views here — that is P1.10/P1.11. This ticket only defines and proves them.
- Keep the set small. A token nobody consumes is dead weight; add on demand later.

## Rulings that unblock P0.4 (added 2026-07-25 by the supervisor)

P0.4 built the contrast gate and found **177 failing pairs / 29 distinct colour pairs** in the real
view tree (see `P0.4-FINDINGS.md`, which lists every pair with its measured ratio). It correctly
refused to allowlist them or to recolour the app outside its scope. Those failures are **this
ticket's input**. The four open questions are ruled as follows — they implement the already-locked
"real light + dark, contrast-gated in both" decision, so they are not new design latitude:

1. **House muted text — do not use Apple's semantic label colours on custom fills at all.**
   `secondaryLabelColor` (black@0.50 → `#808080` → 3.95:1) and `tertiaryLabelColor` (~2.25:1) cannot
   clear 4.5:1 by construction. Define `textSecondary` explicitly: on dark surfaces ~white@0.70, on
   light surfaces ~black@0.65, then **verify by computation against every documented surface** and
   adjust until every pair clears 4.5:1. Unblocks the 74-pair root cause.

2. **Accents need a darker light-appearance variant.** The status accents fail as *text* on light
   backgrounds (~44 pairs). Give each accent a `TokenColor` whose `light` value is a darkened variant
   (roughly the -600/-700 range) and whose `dark` value is the lighter one (~-300), keeping the hue
   identity stable so a status reads the same across themes. Accent-as-fill and accent-as-text are
   different jobs — if a single value cannot serve both, add `accentXText`.

3. **Card surfaces are appearance-aware.** In light theme the card fills become light surfaces with
   dark text; they do **not** stay dark. Keeping dark fills under light appearance *is* the shipped
   bug (~25 pairs of black-on-dark). Unblocks that root cause.

4. **Border policy — meaningful borders ≥3:1; purely decorative hairlines exempt, but listed.**
   Per WCAG 1.4.11, the 3:1 requirement covers borders that delineate an interactive control or
   convey state (focus, selection, attention). A hairline that is pure visual separation *inside* an
   already-delineated surface is exempt. Every exemption goes in a short, commented list naming why
   — never a blanket waiver. Note that the tile border at 1.68:1 is **not** decorative: it delineates
   the tile as an object, so it must clear 3:1 (this is the "canvas looks like mush" defect).

## Enablement of the P0.4 leg belongs to P1.6
`--ui-contrast-check` exists and is deliberately **not** wired into `run-matrix.sh`. P1.6 turns it on
once these tokens land. That ordering is the point: the tokens are chosen against a gate that already
measures the real view tree.
