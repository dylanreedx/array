# P0.4 findings — the contrast gate works, and it is red on 177 real pairs

Status: **P0.4 is blocked.** The gate is built, committed, and correct. Its matrix leg is
deliberately **not** wired in, because turning it on today makes the matrix red and the packet
forbids the only two ways to make it green without the owner.

## What landed

- `Sources/ContinuumRevived/App/UIProbeContrast.swift` — the gate.
- `--ui-contrast-check` in `ContinuumApp`, so the owner can run it in one command:

  ```
  swift build && CONTINUUM_SKIP_SURFACE_CHECKS=1 \
    .build/debug/continuum-revived --ui-contrast-check
  ```

- **No leg in `scripts/run-matrix.sh`.** The matrix is green as of this commit and the loop can keep
  going; nothing passes silently, because the gate is not claimed to be passing anywhere.

## The gate is correct — evidence, not assertion

It measures 446 pairs across every static Component Lab card in both appearances — 402 text, 30
layer borders, 14 explicitly tinted glyphs — and **269 of them pass** (149/402 text and 28/30 borders
fail; every glyph passes). It is discriminating, not uniformly rejecting.

The compositing path is confirmed against AppKit's documented semantic-colour alphas — these are
derived numbers that could only come out right if the walk, the alpha composite, and the sRGB
conversion are all correct:

| measured | AppKit colour | expected | check |
|---|---|---|---|
| `#808080` on `#FFFFFF` = 3.95:1 | `secondaryLabelColor` = black@0.50 in Aqua | 255·(1−0.50) = 128 = `#80` | ✓ |
| `#BDBDBD` on `#FFFFFF` = 1.88:1 | `tertiaryLabelColor` = black@0.26 in Aqua | 255·(1−0.26) = 189 = `#BD` | ✓ |
| `#565656` on `#1E1E1E` = 2.26:1 | `tertiaryLabelColor` = white@0.25 in DarkAqua | 30+0.25·(255−30) = 86 = `#56` | ✓ |

Ratios come from `WCAGContrast` (Core), already gated by `runStatusChipChecks`.

**The 177 are not measurement artifacts.** Codex's review found four real defects in the first draft
— ancestor alpha applied to foregrounds but not to fills, `layer.opacity` ignored, `NSTextView` /
`NSScrollView` / `NSTableView` own fills not read (the tile text views set `backgroundColor` directly,
so their glyphs were being measured against the window fill), and glyph tints not gated at all. All
four are fixed. Coverage went from 432 pairs to 446 and **the failing set did not move: still exactly
the same 177**. The added fills and glyphs all pass, so no failure here was ever an artifact of the
missing cases.

Known limit, documented in the source: a background painted in a custom `draw(_:)` override cannot be
read off any property, so such a view's text is measured against the nearest *readable* fill.
Pixel-level sampling is `P0.5-pixel-probes`.

## The 177 failures are 29 distinct colour pairs, in four root causes

### 1 · Apple's own secondary/tertiary label colours do not clear 4.5:1 — 74 pairs
`secondaryLabelColor` is 3.95:1 on white; `tertiaryLabelColor` is 1.88:1 on white and 2.26:1 on the
dark window fill. These are **stock AppKit colours**, not this program's.

A 4.5:1 gate over the whole view tree therefore forbids AppKit's standard secondary-text colours
anywhere in the app. That is a defensible product decision — but it *is* a product decision, and
honouring it means inventing a house muted-text colour with a value for each appearance. That is
`P1.3-surface-text-border-tokens` plus `P1.6-token-contrast-gate`, not this ticket.

### 2 · Black text on hardcoded dark fills in Aqua — ~25 pairs
The bug the packet's Goal narrates, now measured: `#040506` on `#1C2129` = 1.26:1,
`#050607` on `#21262E` = 1.34:1 (managed-agent tile header and transcript cards). A dynamic label
colour resolving to black over an unconditionally dark fill. **This one is unambiguously a bug** and
needs no taste call — but the fix is either "make the fills appearance-aware" or "make the text
explicitly light", and that choice is the token system's to make.

### 3 · Accent colours used as text on white — ~44 pairs
`#FF8D28` (2.31:1), `#0088FF` (3.52:1), `#34C759` (2.22:1), `#CB30E0` (4.17:1), `#007AFF` (4.02:1),
`#FFA24F` (2.00:1), `#2E9DFF` (2.83:1). Status/badge accents doubling as label colours. Fixing them
means darker light-appearance variants of each accent — i.e. the light half of the status palette,
which is `P1.2-tokencolor-light-dark`.

### 4 · Hairline borders below 3:1 — 28 pairs
Card and tile borders at 1.56–1.68:1 against their own fill (`#404040` on `#1A1A1A`,
`#40454B` on `#21262E`), and the approval dock at 2.86:1 / 2.92:1 — just under.

Worth the owner's eye: WCAG 1.4.11's 3:1 applies to boundaries needed to *identify a control*. A
decorative 1pt card divider is arguably out of its scope, and taking these to 3:1 is a visible
design change (chunky, high-contrast card outlines). The dock at 2.86:1 is a near-miss that is
clearly worth just fixing. Either way it is a threshold decision, and the packet's instruction is
that a failing pair means the colour is wrong — so the gate cannot decide this itself.

## Why this is blocked rather than fixed or allowlisted

The packet's `## Files` names exactly two files: the new gate and `run-matrix.sh`. No view files. A
packet authored zero-guessing would have named ~20 view files if a recolour of the whole app were in
scope. The author expected a handful of failures, not 177 across 29 colour pairs.

The two available routes to green are both closed:

- **Allowlist them** — `## Watch out` forbids it outright: "Do not 'fix' a failure by widening the
  allowlist. If a pair fails, the colour is wrong."
- **Recolour the app now** — that is `P1.2`/`P1.3`/`P1.10`/`P1.11` (light+dark tokens, then adopt
  them in tile and chrome), done by hand in raw colours before the token system exists, and rewritten
  by Phase 1 immediately afterwards. It is also a design decision the runbook says may not be
  certified by eye.

## What the owner needs to decide

1. **House muted-text colour** for both appearances, replacing `secondary`/`tertiaryLabelColor`
   (≥4.5:1 on both window fills). Unblocks 74 pairs.
2. **Light-appearance variants of the status accents** (orange / blue / green / purple). Unblocks ~44.
3. **Fills vs text for the dark card surfaces** — appearance-aware fills, or explicitly light text.
   Unblocks ~25. This one is a real shipped bug either way.
4. **Whether decorative borders are held to 3:1**, or only borders that delineate a control (with the
   gate's border threshold scoped accordingly). Unblocks 28.

## Recommended sequencing

Fold P0.4's enablement into Phase 1: land the light+dark tokens (`P1.2`, `P1.3`), then turn this leg
on as part of `P1.6-token-contrast-gate` — the tokens are chosen against a gate that already exists
and already measures the real view tree. P0.7 (retire the `isBlank` gate) depends on P0.4, so it
stalls until then; P0.5, P0.6 and P0.9 do not and can proceed.

Nothing here needs re-deriving: re-run the command at the top and the same 177 lines print, each with
its measured ratio, its foreground, and its background.
