# P4.14 — A row stuck on "working" forever

Phase: 4 · Depends: P2A.3, P2B.4, P4.2

**PULLED FORWARD — the owner hit this in the shipped build on 2026-07-26.** Their words:

> "the sidebar appears to be out of sync with the agents... i typed a simple prompt, went to working,
> then done but sidebar is stuck in working"

They are right, it is fully diagnosed below, and it is not a refresh bug. **This is the highest
priority ticket in the queue.**

## Root cause — measured, not inferred

The sidebar row is displaying **process liveness** as though it were **turn activity**. Those are two
different axes and the code collapses them.

1. `ManagedSessionStatus` (`Sources/ContinuumRevivedCore/ManagedAgentSessionRecord.swift:3`) has
   exactly four cases: `starting`, `running`, `stopped`, `error`. **There is no case for "the session
   is alive and idle between turns"** — which is the state an agent spends almost all its life in.

2. `ContinuumApp.swift:4160` maps it straight onto the displayed status:

   ```swift
   private static func agentStatus(for managedStatus: ManagedSessionStatus) -> AgentStatus {
       switch managedStatus {
       case .starting: return .configuring
       case .running:  return .working      // <- the bug
       case .stopped:  return .idle
       case .error:    return .needsAttention
       }
   }
   ```

3. **Nothing in the shipped app ever writes a `ManagedSessionStatus`.** A repo-wide grep for
   `ManagedSessionStatus.` outside check code returns **zero** hits. The record is written once at
   creation and its `status` never transitions. On the owner's machine right now, the persisted
   records read `{'status': 'running'} ×3` and `{'status': 'starting'} ×1`, with no turn in flight.

So `running` is written once, never cleared, and rendered as "working" indefinitely. The tile shows
the truth because it consumes the live event stream; the sidebar shows a stale persisted field.

## The fix, and why it is a derivation and not a new write

**Do NOT "just write `.stopped` when the turn ends."** That spelling says the *session* stopped, which
is false — the session is alive and ready for another prompt, and `.stopped → .idle` would also make
a live agent indistinguishable from a dead one. It would trade a stuck row for a lying row.

**Turn state already exists and is authoritative.** `AgentSupervisor` knows whether a turn is in
flight: it holds `runners[id]` for exactly the duration of a turn and **refuses** a second prompt
while one is live (`P2A.3`'s fixed HIGH). It emits `turnStarted` / `turnCompleted`, and persists the
record on precisely those lifecycle events. `P2A.6` built a view-free status derivation, `P2B.4`
collapsed four derivations into one snapshot, and `P4.2` established that work needing a human
outranks "I said done". The row's status must come from that derivation — not from a persisted
process-liveness field.

Preferred shape, in order:

1. **Derive `working` from turn state**, not from `ManagedSessionStatus`. An agent is `working` when
   its supervisor has a live runner (or its last event was `turnStarted` with no matching
   `turnCompleted`); otherwise it is `ready`/`idle`, with `P4.2`'s blockers and `P4.1`'s override
   taking precedence as they already do.
2. **If the persisted field must stay in the derivation at all**, it may only contribute the states it
   can actually witness — `starting` before the first event, `error` — and must never be the source of
   `working`.
3. **Only if 1 and 2 cannot express the restored-from-disk case**, add an explicit `idle`/`ready` case
   to `ManagedSessionStatus`. That is a persisted schema change: bump `schemaVersion`, decode forward
   with `decodeIfPresent`, and read the version off the payload rather than clamping it — `P2A.1`
   established all three and proved them with a 200-value sweep.

`updatedAt: record.lastActivityAt` is already carried into the scan (`ContinuumApp.swift:4153`), so
staleness is available if a freshness window helps. **A timeout is not a fix on its own** — a row that
self-corrects after N seconds is still wrong for N seconds, and `PiAgentStateReader` already shows
where that pattern belongs (`freshWorkingWindow`, for a *foreign* process nobody notifies us about).
Here we own the events.

## Done when

- An agent that finishes a turn reads **done/ready** in the sidebar, with no relaunch and no waiting.
- An agent mid-turn reads **working**.
- A restored-from-disk agent with no live runner does **not** read working.
- A dead/stopped session is still distinguishable from a live idle one.
- The tile and the row agree at every point in a turn — that agreement is the ticket.
- Full matrix green, no floor lowered, no check loosened.


Drive it through `--agent-supervisor-check`, which already runs a scripted 8-event turn with a
`ScriptedAgentRunner` behind the two-method `AgentRunning` protocol — no Pi, no network, no
wall-clock. Assert the derived row status **across the whole turn**: before `turnStarted`, between
`turnStarted` and `turnCompleted`, and after `turnCompleted`. The last of those is the owner's bug.

**Required red-green witnesses** (each observed red at exit 1 against the FINAL code, failure text
quoted verbatim at the assertion):

1. `agentStatus(for:)` restored to mapping `.running → .working` → the after-`turnCompleted`
   assertion goes red. **This is the witness for the reported bug and it must fail loudly.**
2. A restored agent with a persisted `running` status and NO live runner → must not read working.
   This is the owner's exact on-disk state (`{'status': 'running'}` with nothing running) and a
   fixture that omits it leaves the bug reachable.
3. Mid-turn status → must read working. The pair to 1; without it "never working" passes.
4. A live idle session vs a stopped one → must be distinguishable. Guards the lazy `.stopped` fix.
5. `P4.2` precedence intact: an agent needing approval outranks both working and settled.
6. `P4.1`'s explicit override still respected.

Then confirm the whole-turn agreement between the tile's ingested state and the derived row status in
one assertion, so the two cannot drift again.

Do not run `--managed-agent-live-check` (needs Pi auth and a supervised GUI; blocks on an `NSAlert`
unattended, recorded under `P0.8`). A real prompt-to-done pass is a supervised step — note it as owed.

## Watch out

- **This is a status DERIVATION change, so every consumer moves at once**: the sidebar outline, the
  inbox rows, the zone rollups, ⌥-agent-cycle, the dock badge and the phone timeline all read
  `P2B.4`'s one snapshot. That single source is exactly why the fix belongs there — but check each
  consumer's expectations rather than assuming, and re-read `P2B.5`'s witnesses ("a managed-agent tile
  must show its record's status in the sidebar — got 'no agent'").
- **Zone rollups will change counts.** A project full of agents that all falsely read "working" is
  currently rolling up as N working. Fixing this will move those numbers — that is the fix landing,
  not a regression, but say so in the ledger with before/after figures.
- **The phone must not regress**, and I5 still holds: only derived metadata crosses the boundary, no
  paths, transcripts, pids or secrets.
- **`.starting` is legitimate** — it is the pre-first-event state and `configuring` is the right
  reading of it. Do not collapse it into idle.
- Terminal-hosted agents go through `PiAgentStateReader`, a different path with its own freshness
  window for a process nobody notifies us about. **Do not change it here.**
- Do not touch delete/archive (`P3.15`), the inbox filter (`P3.16`), or the transcript (`P6.0`).
