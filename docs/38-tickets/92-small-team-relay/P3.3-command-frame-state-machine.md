# P3.3 — Command Frame State Machine

Phase: 3 · Typed protocol and production transport
Execution: **autonomous**
Depends on: P3.2

## Goal

Add typed command submit/ack/receipt/reconcile frames for prompt, follow-up/steer, approval, stop, abort, and constrained agent creation.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Commands are explicit product actions, not generic remote procedure calls or shell strings. Every submission carries an idempotency key and maps to the durable receipt model.

## Approach

1. Define distinct payloads for prompt.send, agent.steer/followUp, approval.respond, agent.stop, agent.abort, and agent.create.
2. Require commandID, device idempotency key, target agent/environment, catalog revision where relevant, and no arbitrary cwd/env/provider secret fields.
3. Define host ack and reconciliation query/result separate from terminal receipt.
4. Pin capability and offline policy for every command kind.

### Implementation sketch

```text
command.submit(idempotencyKey, target, typedAction)
command.hostAck(commandID)
command.receipt(commandID, state, safeResult)
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Done when

- Each command fixture has exact required capability, size limit, offline behavior, and receipt transitions.
- Conflicting idempotency-key payloads fail before forwarding.
- There is no generic execute/shell/tool-invoke command.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

- Stop and abort are not aliases.
- Approval options must match an outstanding provider request.
