# P2.8 — Auth Rate Limits Redaction

Phase: 2 · Identity and authorization
Execution: **autonomous**
Depends on: P2.7

## Goal

Add bounded authentication/pairing/command/blob rate limits and centralized privacy-safe security diagnostics.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Private networking reduces exposure but does not excuse brute force, accidental loops, or logs containing credentials/transcripts. Limits must be deterministic, per-principal/source where appropriate, and cheap before decode/database work.

## Approach

1. Implement token buckets with injected monotonic clock and bounded durable state only where restart reset would be unsafe (pairing/auth).
2. Key unauthenticated limits by privacy-preserving source fingerprint supplied by the server adapter; authenticated limits use principal ID.
3. Create structured diagnostics containing IDs/fingerprints/counts only—never auth headers, pairing secrets, APNs tokens, transcript/tool bodies, or environment values.
4. Apply cost ordering: header/frame size → rate limit → auth → full decode/store.

### Implementation sketch

## Done when

- Exact burst/refill/restart behavior is checked without sleeps.
- A corpus of secret/transcript/tool values is absent from encoded logs and errors.
- Rate-limit refusal does not reveal whether a pairing secret or device exists.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.
