# P2.7 — Expiry Revocation Eviction

Phase: 2 · Identity and authorization
Execution: **autonomous**
Depends on: P2.6

## Goal

Make device, membership, and environment expiry/revocation disconnect active sessions and prevent replay or command activity without restarting the relay.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

A durable revoked flag is insufficient if an already-authenticated WebSocket remains privileged. The session registry needs a reverse index and explicit eviction cause.

## Approach

1. Index active session IDs by principal and workspace memberships.
2. On revoke/expiry/membership removal, commit durable state first, then close affected sessions with a non-secret machine-readable reason.
3. Check authorization again at command/publish admission so a race cannot use a stale session grant.
4. Inject clock advancement; do not wait real minutes.

### Implementation sketch

```text
try store.revoke(principalID)
for session in sessions.forPrincipal(principalID) { session.close(.credentialRevoked) }
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Done when

- Active streams terminate promptly after durable revocation and cannot submit one final accepted command.
- Restart retains revoked state.
- Revoking one workspace membership does not evict unrelated authorized workspace sessions unless session multiplexing makes selective removal unsafe.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

## Watch out

- Do not close before commit and then report successful revocation if persistence failed.
- Do not include credential/token material in close reasons.
- Expiry checks need bounded clock skew policy.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
