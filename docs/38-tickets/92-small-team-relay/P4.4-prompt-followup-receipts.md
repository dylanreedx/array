# P4.4 — Prompt Followup Receipts

Phase: 4 · Full-control host and phone flows
Execution: **autonomous**
Depends on: P4.3

## Goal

Wire prompt.send and provider-supported follow-up/steer from Mac/iPhone through durable receipts to the real host agent gateway.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Submitting text is a user-visible execution path. The same idempotency key must return the same receipt across button retries, reconnect, relay restart, and ambiguous host timing.

## Approach

1. Create client idempotency keys before submission and persist pending UI state until a durable receipt arrives.
2. Host distinguishes new prompt, follow-up, and steer by compiled provider capability; unsupported actions are absent/refused, not simulated.
3. Append the user prompt semantic mutation exactly once from the authoritative accepted command path.
4. Inject relay/host/provider crash points before receipt, after forward, after host ack, and after provider outcome.

### Implementation sketch

```text
key = draft.persistedIdempotencyKey
receipt = await relay.submit(.prompt(text), key)
UI renders receipt; host gateway dispatches only from received command ID
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Done when

- Double-tap/retry/reconnect produces one host gateway dispatch and one user transcript entry.
- Offline environment refuses before forwarding and leaves draft recoverable.
- Ambiguous provider boundary yields indeterminate and requires explicit user retry/reconcile.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.
