# P3.1 — Relay Frame Envelope Versioning

Phase: 3 · Typed protocol and production transport
Execution: **autonomous**
Depends on: P2.9

## Goal

Define the bounded, tagged RelayFrame envelope, protocol negotiation, message identity, and compatible-major version rules in RelayProtocol.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

The old RelayWire embeds a bearer token in hello and carries generic SyncMessage envelopes. The hardened protocol keeps credentials in transport headers and uses typed families with explicit versioning.

## Approach

1. Create protocolVersion, messageID, workspaceID and optional environmentID/agentID plus a tagged payload.
2. Define hello/welcome/error/ping/pong first; credentials stay in HTTP/WebSocket authentication, never RelayFrame JSON.
3. Unknown major versions refuse; unknown optional fields within the current major are ignored; unknown payload kinds deny safely.
4. Enforce depth/string/collection/envelope limits before or during decode through an owned bounded decoder seam.

### Implementation sketch

```text
struct RelayFrame { version; messageID; workspaceID?; payload: RelayPayload }
negotiate(clientMajors, serverMajor) -> acceptedVersion | unsupported
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.
