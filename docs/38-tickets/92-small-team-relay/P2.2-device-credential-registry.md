# P2.2 — Device Credential Registry

Phase: 2 · Identity and authorization
Execution: **autonomous**
Depends on: P2.1

## Goal

Persist server-generated high-entropy device credentials as hashes with expiry, last-used, label, and revocation metadata.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Bearer credentials are acceptable for this small trusted deployment only if the server generates them, stores no plaintext, and can revoke them durably. Tests must use injected entropy and clock.

## Approach

1. Add a reviewed exact/compatible `swift-crypto` dependency to RelayCore so hashing and signing primitives remain portable to Linux; update the target-boundary check rather than importing Apple-only CryptoKit.
2. Generate 256-bit credentials from an injected CSPRNG in production; expose plaintext exactly once to the caller.
3. Store SHA-256 credential digest plus per-record identifier/metadata; compare in constant-time over fixed-size digests.
4. Authenticate by hashing presented bytes, checking expiry/revocation, and updating last-used through a bounded write policy.
5. Redact credentials from descriptions, Codable errors, and logs.

### Implementation sketch

```text
raw = entropy.bytes(count: 32)
digest = SHA256(raw)
store(device, digest, metadata)
return oneTime(raw)
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Watch out

- Do not use UUID strings or human pairing codes as long-lived credentials.
- Do not log even token prefixes; fingerprints derive from digest metadata.
- Keychain storage is a client ticket, not a reason to return the credential twice.
- Do not use Apple-only CryptoKit in RelayCore; the Linux source/dependency gate must compile the same credential semantics.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
- If the packet conflicts with compiled reality or an unresolved owner decision, return `WORKER: BLOCKED <evidence>` rather than inventing a second architecture.
