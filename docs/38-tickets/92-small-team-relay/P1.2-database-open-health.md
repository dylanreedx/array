# P1.2 — Database Open Health

Phase: 1 · Durable single-node state
Execution: **autonomous**
Depends on: P1.1

## Goal

Implement safe database opening, WAL/busy/foreign-key configuration, migration locking, integrity readiness, and explicit startup failure behavior.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

A single-node service still has concurrency and corruption boundaries. Opening a database must not silently replace, truncate, or migrate a file when the directory or schema is unsafe.

## Approach

1. Accept an explicit data-directory URL and create only relay-owned children with restrictive permissions.
2. Apply WAL, foreign_keys=ON, bounded busy timeout, and synchronous policy; read back every pragma in checks.
3. Serialize migrations and expose liveness separately from readiness. Readiness fails on migration debt, integrity failure, unwritable data/blob directory, or identity mismatch.
4. Inject filesystem/database faults; never call exit from RelayCore.

## Done when

- Two concurrent open/migrate attempts converge or return a named busy error without partial schema.
- Wrong permissions, corrupt bytes, and future schema version fail closed and preserve the original file.
- WAL and foreign-key settings are measured on the actual connection pool.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

- Tests use temporary directories and restore their permissions.
