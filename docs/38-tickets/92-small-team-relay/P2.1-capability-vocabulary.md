# P2.1 — Capability Vocabulary

Phase: 2 · Identity and authorization
Execution: **autonomous**
Depends on: P1.10

## Goal

Define an extensible, canonical capability vocabulary and server-owned role templates for transcript, tools, prompts, steering, approvals, stop, creation, device, workspace, and relay administration.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

The current Scope OptionSet and RelayGrant.canPublish conflate observation, publication, operation, and token enrollment. Privileged routes need exact named capabilities and deny-by-default decoding.

## Approach

1. Use validated string capability keys so future readers can preserve unknown values but never grant them implicitly.
2. Define viewer, operator, workspaceAdmin, relayAdmin, and executionHost templates in RelayCore, not request DTOs.
3. Separate publish-own-environment from human command capabilities.
4. Canonicalize sets for storage/audit and reject duplicates/invalid syntax.

### Implementation sketch

```text
required(frame.kind) -> Set<RelayCapability>
granted = serverRoleTemplate(role) + explicitAdminOverrides
authorize iff required ⊆ granted
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.
