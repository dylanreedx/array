# P3.10 — Transport Security Supervised Review

Phase: 3 · Typed protocol and production transport
Execution: **supervised**
Depends on: P3.9

## Goal

Supervise the first hardened real-process transport, choose the deployment route/budget, and clear auth/isolation/fault evidence before any full-control command integration.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

This gate is intentionally human-supervised because binding, TLS/private-network trust, low-cost hosting, and recovery custody are owner decisions. No agent may silently choose a public endpoint or mark a source-only security claim accepted.

## Approach

1. Resolve first host: existing office hardware or an owner-approved approximately $5/month VPS. Record provider, region, storage, backup, firewall, and monthly ceiling without committing credentials.
2. Choose LAN/VPN/private mesh versus public TLS. If public, inspect certificate termination, firewall, patching, rate-limit, and restore posture.
3. Run two-workspace auth tests, revocation of a live socket, malformed/oversized frame corpus, slow consumer, relay kill/restart, database fault, and endpoint-substitution checks against a real process.
4. Record explicit owner approval or correction packets; keep the loop stopped until the decision file is complete.

### Implementation sketch

```text
OWNER GATE: deployment + trust + budget + endpoint
SECURITY GATE: real process + two workspaces + fault corpus
result = approve | corrections-required
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Done when

- Owner records the selected deployment route, budget cap, trust boundary, and backup custody.
- Real-process evidence clears route authorization, revocation, limits, restart replay, and secret-log scans.
- No production port is opened merely to complete this ticket.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

## Watch out

- Do not paste VPS, VPN, APNs, or recovery credentials into docs/qa logs.
- A managed TLS provider can read Class-B content unless end-to-end encryption is later added.
- If owner decisions are unavailable, remain supervised/blocked; do not skip ahead.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
- If the packet conflicts with compiled reality or an unresolved owner decision, return `WORKER: BLOCKED <evidence>` rather than inventing a second architecture.
