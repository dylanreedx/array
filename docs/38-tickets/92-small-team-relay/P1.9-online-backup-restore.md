# P1.9 — Online Backup Restore

Phase: 1 · Durable single-node state
Execution: **autonomous**
Depends on: P1.8

## Goal

Implement consistent online backup and isolated restore validation for the database, blob manifest, relay identity, and configuration manifest.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Copying a live SQLite file is not a backup. The operator needs an encrypted-archive input that can be integrity-checked without activating a second relay identity.

## Approach

1. Use GRDB/SQLite online backup to a staging directory while event writes continue.
2. Create a canonical manifest with schema version, relay identity fingerprint, database hash, blob hashes/sizes, and creation time from an injected clock.
3. Separate archive construction from encryption transport: v1 emits an owned staging bundle to a caller-supplied encryptor; plaintext staging is permission-restricted and deleted on completion/failure.
4. Restore validates in an isolated directory, runs integrity/schema/blob checks, and refuses activation while the original identity is live.

### Implementation sketch

```text
staging = secureTemporaryDirectory()
try sqliteOnlineBackup(to: staging/db)
manifest = hash(db + referencedBlobs + identityFingerprint)
return encryptor.seal(staging, manifest)
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Done when

- Concurrent writes yield a self-consistent database snapshot and matching referenced blobs.
- Missing, extra, corrupt, or swapped blob/database bytes fail validation by exact code.
- Restore checking has no effect on active relay files or network listeners.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

## Watch out

- Do not put the administrator recovery secret in plaintext manifest fields.
- Do not assume filesystem encryption follows an archive off-host.
- Do not run original and restored copies with the same identity concurrently.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
- If the packet conflicts with compiled reality or an unresolved owner decision, return `WORKER: BLOCKED <evidence>` rather than inventing a second architecture.
