# P1.1 — Sqlite Migration Spine

Phase: 1 · Durable single-node state
Execution: **autonomous**
Depends on: P0.5

## Goal

Add the versioned SQLite migration spine for relay-owned state with all tables, keys, uniqueness constraints, and foreign-key relationships required by the approved model.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Schema shape is a contract. This ticket creates migrations and schema introspection only; repositories and behavior arrive in later packets. Use SQLite-compatible primitives and explicit migration names so restore and downgrade diagnostics are possible.

## Approach

1. Create tables for relay metadata, workspaces, devices, memberships, pairing grants, environments, agents, events, snapshots, commands, blobs, push tokens, and rate-limit buckets.
2. Pin unique constraints on credential hashes, membership pairs, event cursor triples, device idempotency keys, and blob hashes.
3. Enable foreign keys and explicit delete policies; transcript deletion must not orphan blobs or receipts silently.
4. Check empty-to-latest and every-prefix-to-latest migration using temporary files.

## Done when

- Duplicate event cursors and idempotency keys fail at SQLite, not only Swift.
- No production repository API exists yet.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.

## Watch out

- Do not store raw credentials in any column.
- Do not use cascade deletion where audit/receipt retention semantics are unresolved.
- Do not put host filesystem paths in blob records.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
- If the packet conflicts with compiled reality or an unresolved owner decision, return `WORKER: BLOCKED <evidence>` rather than inventing a second architecture.
