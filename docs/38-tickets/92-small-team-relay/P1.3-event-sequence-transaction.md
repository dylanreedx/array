# P1.3 — Event Sequence Transaction

Phase: 1 · Durable single-node state
Execution: **autonomous**
Depends on: P1.2

## Goal

Persist agent events with atomic generation/sequence allocation and deterministic duplicate/conflict handling.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Clients must never observe a cursor that cannot be replayed. Sequence assignment belongs in the same database transaction as event insertion, not in actor memory or after serialization.

## Approach

1. Define RelayEventCursor(generation, sequence) with checked nonzero generation and monotonic sequence.
2. Allocate next sequence and insert canonical payload bytes in one immediate transaction.
3. An identical retry at the same host event ID returns the original row; different bytes for the same identity return conflict.
4. Refuse sequence overflow and generation rollback explicitly. Exercise concurrent writers with deterministic barriers.

### Implementation sketch

```text
db.inTransaction {
  current = loadAgentCursor(agentID)
  next = checkedIncrement(current)
  insert(event, cursor: next)
  updateAgentCursor(next)
  return next
}
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Done when

- Committed cursors are contiguous under concurrent writers and restart.
- Injected failure between allocation and insert leaves neither a gap nor advanced agent cursor.
- Duplicate-identical and duplicate-conflicting behavior is exact and named.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

## Watch out

- Do not use wall-clock order as sequence order.
- Do not decode/re-encode payload JSON during replay; canonical bytes are part of conflict detection.
- Generation change requires an explicit reset/reconciliation reason.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
