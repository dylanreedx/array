## Outcome

Continuum should ship a **boring, single-node Array Relay** for Dylan and a small office rather than reproduce T3 Connect’s public multi-tenant cloud. One relay process runs on existing Mac or Linux hardware, uses SQLite WAL and local blob storage, accepts Mac/iPhone clients over LAN or a private network, and maintains durable transcript replay and command receipts. Execution hosts retain provider credentials, environment variables, raw processes, signing keys, and filesystem authority.

**Done means:** closing the Mac app does not stop an awake relay service; restart does not lose pairings, transcript history, cursors, commands, or push registrations; a paired phone can read full authorized transcripts and perform explicit agent actions; an execution Mac that sleeps is shown honestly offline; another awake host can continue; every mutation is capability-checked and idempotent; and the normal deployment remains within the owner-approved approximately $5/month budget.

<Callout id="small-team-decision" tone="decision">
**Product boundary:** target one trusted relay, approximately 10 teammates, 30 devices, 20 execution environments, 100 active/recent agents, and up to 100 concurrent sockets. Prefer vertical simplicity and explicit limits. Public signup, untrusted tenants, automatic per-user tunnels, globally replicated storage, and horizontal failover are outside this plan.
</Callout>

## Concrete product scenario

Dylan runs Array Relay on an existing always-on office Mac mini. His development Mac, a teammate’s Mac, an iPhone, and an optional Linux build host pair once. Each execution host makes one authenticated outbound WebSocket connection to the relay. Clients see only workspaces they are allowed to access.

Dylan starts an agent on his development Mac, reads structured transcript and tool output from his phone, answers an approval, and sends a follow-up. The host commits provider-neutral transcript events locally and publishes them to the relay. The relay commits each accepted event before broadcasting it to clients. If the development Mac sleeps, the phone continues to read the relay’s durable transcript mirror but shows the agent as offline and refuses new execution commands. A Linux build agent remains controllable because its host is still awake.

The relay administrator can list devices, revoke a lost phone, rotate an execution-host credential, inspect storage usage, create an encrypted backup, and restore the same relay identity on replacement hardware.

### Authority boundaries

- **Execution host:** final authority over provider calls, tools, projects, processes, and approvals that touch host resources. It may reject any relayed command.
- **Relay:** trusted office identity and routing authority. It authenticates devices/hosts, enforces workspace membership, stores the client-facing event mirror, assigns durable relay cursors, and records command outcomes.
- **Client:** presents authorized state and submits explicit commands. It never receives provider credentials or a generic remote shell capability.
- **APNs:** receives only sanitized Class-A notification projection; opening the app fetches authenticated content from the relay.

This is deliberately less decentralized than a public T3-like system. The relay host and its backups are sensitive infrastructure and must be protected accordingly.

## Identity, pairing, and recovery

<Callout id="auth-decision" tone="decision">
The relay host is the small team’s trust root. Recovery consists of the relay identity, an administrator recovery key, the SQLite database, and the blob directory in an encrypted backup. There is no hosted account and no distributed owner certificate chain in the first release.
</Callout>

### Device pairing

1. An administrator creates a pairing invitation with an exact workspace role and five-minute expiry.
2. The QR carries a 256-bit random one-use secret. A manual fallback uses a rate-limited high-entropy code.
3. Exchange is atomic: the first successful exchange consumes the invitation; concurrent or expired attempts fail.
4. The relay creates a device record and returns a 256-bit opaque credential. The client stores it in Keychain.
5. The relay stores only `SHA-256(credential)` plus device, expiry, last-used, and revocation metadata.
6. Requests are accepted only over approved TLS/private-network routes and are checked against the stored device/workspace capabilities.
7. Administrators can list, revoke, expire, and rotate devices without restarting the relay.

### Execution-host pairing

Execution hosts receive separate environment credentials and cannot act as human devices. Hosts connect outbound, advertise configured workspaces/projects/providers, and prove liveness with a renewable lease. A host credential is scoped to one environment ID and may publish events or consume commands only for its configured workspaces.

### Session policy

The first release uses opaque bearer credentials rather than JWT/DPoP. That is acceptable only with TLS/private-network transport, Keychain storage, high entropy, server-side expiry, revocation, rate limiting, and log redaction. A device credential is never accepted in URL query parameters. Protocol traces show only credential fingerprints.

### Persistence rules

- Configure SQLite WAL, foreign keys, busy timeout, full migration history, and bounded transaction durations.
- Assign `(generation, sequence)` and insert the event in one transaction. Broadcast only after commit.
- Use a new generation only when an environment loses/rebuilds its local log; never reset a sequence silently.
- Create periodic semantic snapshots. Cold clients load the newest snapshot and replay the tail.
- Enforce uniqueness on `(agent_id, generation, sequence)` and `(device_id, idempotency_key)`.
- Keep transcript events until explicit archive/delete. Apply quotas to blobs and unusually large tool output.
- Store blobs below a relay-owned directory by content hash. Never accept a caller-supplied filesystem path.
- Use OS full-disk encryption plus strict file permissions in v1. Backups must be encrypted separately before leaving the host.

## Wire protocol

The existing generic `SyncMessage` remains for spatial/canvas synchronization. Privileged phone control uses a separate, versioned `RelayFrame` vocabulary rather than widening the generic stream.

Each frame carries `protocolVersion`, `messageID`, `workspaceID`, an optional `environmentID`/`agentID`, and a tagged payload. Unknown major versions are refused. New optional fields may be ignored only within a compatible major version. Decode limits are applied before allocating the full payload.

### Backpressure

Each connection has a bounded outbound queue, initially 512 frames or 8 MiB. A slow client is disconnected with its last committed cursor; reconnect uses snapshot plus replay. The relay does not let one phone retain unbounded memory or block event persistence for other clients.

## Transcript contract

The canonical client document is provider-neutral and uses the existing semantic mutation direction in `ContinuumRevivedAgentContent`:

- user and assistant message begin/delta/end;
- provider-supported reasoning-summary begin/delta/end, subject to owner display settings;
- tool-call begin/argument delta/end;
- tool-result begin/delta/end;
- approval or user-input requested/resolved;
- agent status and terminal outcome;
- attachment/blob references;
- explicit redaction or archival mutations.

No event becomes executable HTML. Native renderers handle Markdown, ANSI, links, tool JSON, diffs, and opaque fallback blocks. Unknown provider blocks remain visible as bounded plain/structured content rather than being executed or silently discarded.

- Serialize mutating commands per agent.
- Refuse prompt, steer, approval, stop, and create commands while the target environment is offline; do not silently queue stale execution.
- Persist `received` before forwarding.
- Require the execution host to acknowledge the command ID before the relay records `hostAccepted`.

## Server, networking, and process model

Replace the Darwin-only raw BSD HTTP server with a SwiftNIO adapter while preserving transport-independent actors and deterministic checks.

- HTTP/1.1 and WebSocket support through SwiftNIO/NIOHTTP1/NIOWebSocket.
- TLS normally terminates at the selected private-network/reverse-proxy boundary; add NIOSSL only if direct TLS termination becomes necessary.
- Explicit bind address; loopback default; refuse accidental public wildcard binding unless an administrator acknowledges it.
- Header, body, frame, connection, and request-duration limits.
- Authentication and rate limiting before expensive decode/database work.
- Graceful shutdown stops admission, drains bounded work, commits final state, and closes sockets with a retryable reason.
- `launchd` on macOS and `systemd` on Linux use restart-on-failure. A per-user Mac LaunchAgent survives UI quit but does not promise operation after logout or system sleep.

## Push notifications

Reuse `APNSPushService` and `PushPayloadBuilder` as the Class-A projection boundary. The relay stores APNs device tokens encrypted with relay-local key material and sends directly to APNs when a `.p8` is configured. Notification text remains sanitized; transcript and tool bodies are fetched after the app authenticates.

APNs is optional. Without Apple credentials, the phone reconnects on foreground and receives no remote notification. Failure to deliver a push never changes the durable agent/approval state.

## Operations and recovery

The relay must be operable without a hosted observability stack.

- `/health/live` reports process liveness only; `/health/ready` checks database migration state and writable storage.
- Local structured logs rotate by size/time and redact authorization headers, pairing secrets, APNs tokens, transcript bodies, tool arguments, and environment values.
- A local metrics snapshot reports connections, event commit latency, queue depth, WAL size, workspace bytes, auth failures, rate-limit refusals, APNs outcomes, and oldest unarchived event.
- `continuum-relay status|doctor|devices|revoke|backup|restore|compact` provides the essential administrator workflow.
- Use SQLite’s online backup API, then package the database, blob manifest, relay identity, and configuration into an encrypted archive. Keep a documented retention default such as seven daily and four weekly backups.
- Restore into an isolated directory, run integrity and blob-manifest checks, then deliberately activate the restored relay identity. Never run original and restored copies concurrently with the same identity.
- Migrations are monotonic and transactional. Keep compatibility with one previous wire major during rolling client upgrades; reject unsupported versions clearly.

## Ordered implementation plan

### Phase 0 — freeze contracts and decisions

1. Record the small-team scale target, private-network deployment, trusted-relay authority, transcript mirror, storage quotas, and recovery model as locked decisions.
2. Explicitly supersede current I5 for authenticated Class-B agent content while retaining Class-C host-secret prohibitions.
3. Freeze `RelayFrame`, capability names, `(generation, sequence)`, command state/uniqueness, and error codes before database or UI work.
4. Capture RED evidence for current restart loss, scope enrollment, plaintext in-memory registry, unsafe taint assumptions, and Darwin-only server behavior without changing existing expectations to manufacture acceptance.

### Phase 1 — durable single-node core

1. Add `RelayStore` migrations and repository APIs using existing GRDB.
2. Move token metadata, environment registration, sequences, snapshots, events, command receipts, quotas, and push tokens into SQLite.
3. Commit before broadcast and prove restart/cursor behavior in process-level tests.
4. Add online backup, restore validation, schema migration, and storage accounting before exposing new networking.

### Phase 2 — auth and workspace isolation

1. Implement administrator-created one-use pairing with server-derived capabilities.
2. Stop reusing `CompanionAuthService.activeSessionTokens()` as relay credentials.
3. Add device/environment revocation, expiry, last-seen, active-socket eviction, and rate limits.
4. Generate an authorization coverage test that fails when any route/frame lacks a required capability.

### Phase 3 — production transport

1. Add SwiftNIO HTTP/WebSocket service and retire production reliance on raw BSD long-poll.
2. Add handshake/version negotiation, heartbeat, lease expiry, bounded queues, frame limits, reconnect backoff, and graceful shutdown.
3. Preserve deterministic in-process hub tests and add real-socket process tests on macOS and Linux.
4. Support loopback and private-network configuration first; public wildcard bind remains guarded.

### Phase 4 — full transcript and commands

1. Connect provider adapters to the frozen semantic mutation stream.
2. Persist snapshots and replay the same document mutations on Mac and iPhone.
3. Add prompt, steer/follow-up, approval/user-input, stop, and preconfigured-agent creation commands with durable receipts.
4. Implement offline refusal and indeterminate-dispatch recovery; do not claim exactly-once provider execution.
5. Add content-addressed large-output/blob handling and native non-executable rendering.

### Phase 5 — operations, phone, and push

1. Add admin CLI workflows, health/readiness, local metrics, log rotation, backup scheduling, restore drill, and quota controls.
2. Wire iPhone cache/cursor state, workspace views, full authorized transcript, command receipts, and offline UI.
3. Register APNs tokens and send sanitized direct pushes when configured.
4. Package per-user `launchd` and Linux `systemd` services with explicit awake/logout/reboot semantics.

### Phase 6 — measured office rollout

1. Dogfood loopback, then physical phone over the selected private network.
2. Add one teammate and one additional execution host before broadening membership.
3. Run capacity, crash, network-fault, sleep/wake, backup/restore, credential-revocation, and cross-workspace isolation tests on the actual relay machine.
4. Operate for a defined soak period with storage and latency reports. Consider Cloudflare Tunnel only if private-network onboarding is the demonstrated blocker.

### Required end-to-end smoke

1. Start from an empty relay data directory on the intended host.
2. Initialize the relay and save the administrator recovery material.
3. Pair one Mac execution host and one physical iPhone using a five-minute invitation.
4. Create an agent from a preconfigured project/provider on the phone.
5. Observe user/assistant/tool mutations and submit a follow-up with a stable idempotency key.
6. Kill the relay after forwarding a command, restart it, and verify the existing receipt is returned without blind provider redispatch.
7. Revoke the phone and prove its active socket and subsequent REST/WebSocket requests are rejected.
8. Restore an encrypted backup into an isolated directory, verify database/blob integrity, and confirm transcript replay through the latest committed cursor.

### Real sleep/wake protocol

A phone or VPS must act as the witness because a test runner on the sleeping Mac also stops. Record relay/environment heartbeat timestamps, `pmset -g assertions`, `pmset -g log`, event cursors, command receipts, and provider history across:

- Array window quit while host remains awake;
- screen lock/display sleep;
- idle sleep without a power assertion;
- active-turn idle-sleep assertion when enabled;
- explicit Sleep or `pmset sleepnow`;
- physical MacBook lid close;
- wake and cursor-based recovery;
- development Mac asleep while an awake office/VPS environment continues.

Acceptance requires no claimed local progress during actual sleep, honest offline/read-only phone state, and duplicate-free replay after wake.
