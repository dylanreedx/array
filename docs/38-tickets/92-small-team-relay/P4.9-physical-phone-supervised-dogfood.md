# P4.9 — Physical Phone Supervised Dogfood

Phase: 4 · Full-control host and phone flows
Execution: **supervised**
Depends on: P4.8

## Goal

Supervise a physical iPhone full-control route through the selected network using real transcript replay, prompt, request response, stop, creation, push, revoke, reconnect, and offline state.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Simulator and loopback tests cannot prove APNs, signing, background/foreground, private-network routing, Keychain/Data Protection, or app-switcher privacy. This gate requires Dylan and a real device.

## Approach

1. Install a verified-fresh signed app and pair with a five-minute grant. Confirm relay fingerprint before storing credential.
2. Create an agent from the approved catalog; observe prompt/assistant/tool/reasoning-summary/request mutations; submit follow-up, approval/question response, stop, and supported creation.
3. Background/foreground the app, kill/restart relay, revoke the phone while connected, rotate credential, and inspect cached/offline behavior.
4. Configure sandbox APNs only through local secret storage, send sanitized notifications, inspect lock screen/app switcher, and scan retained artifacts for Class-B/Class-C leaks.

### Implementation sketch

```text
PHYSICAL DEVICE GATE
pair -> transcript -> command receipts -> background/push -> restart/resume -> revoke
owner records approve/corrections
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Done when

- Owner explicitly approves phone behavior and privacy or records correction packets.
- No command is declared verified unless the real host/provider observable changed and the durable receipt/transcript agrees.
- Revoked phone loses active access; chosen cache policy is observed.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

## Watch out

- Never paste APNs .p8, device tokens, bearer credentials, or recovery material into qa-runs.
- A unit/integration test is not substitute evidence for background APNs.
- Keep the loop stopped until owner approval.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
- If the packet conflicts with compiled reality or an unresolved owner decision, return `WORKER: BLOCKED <evidence>` rather than inventing a second architecture.
