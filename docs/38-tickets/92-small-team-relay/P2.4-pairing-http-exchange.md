# P2.4 — Pairing Http Exchange

Phase: 2 · Identity and authorization
Execution: **autonomous**
Depends on: P2.3

## Goal

Expose bounded pairing creation/exchange HTTP DTOs and keychain handoff without preserving the current client-chosen /v1/tokens contract.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

This packet owns transport-independent route handlers, not the NIO socket adapter. Existing /v1/tokens must become deprecated/unreachable on the hardened route before scope escalation can ship.

## Approach

1. Define request/response/error bodies with no scopeRawValue or caller-selected capabilities on exchange.
2. Require relay.admin to create grants; exchange itself authenticates only the one-use secret and request limits.
3. Return credential material once with no-store cache policy metadata and a stable relay identity fingerprint for client confirmation.
4. Add a compatibility refusal for /v1/tokens in the new router and retire the P0.5 client-scope debt flag.

### Implementation sketch

```text
POST /v1/admin/pairing-grants  // admin-fixed grant
POST /v1/pairing/exchange       // one-use secret -> device credential
POST /v1/tokens                 // 410 on hardened router
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.
