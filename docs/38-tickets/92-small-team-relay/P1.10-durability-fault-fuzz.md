# P1.10 — Durability Fault Fuzz

Phase: 1 · Durable single-node state
Execution: **autonomous**
Depends on: P1.9

## Goal

Close the persistence phase with seeded crash/fault/concurrency fuzz covering events, snapshots, commands, quotas, blobs, migration, backup, and restart invariants.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Unit examples are necessary but insufficient for a durable service. This gate must exercise the real temporary SQLite files repeatedly with deterministic operation schedules and injected crash boundaries.

## Approach

1. Generate seeded operation histories across workspaces/agents: append, duplicate, snapshot, command transition, blob attach, archive, backup, close/reopen.
2. Inject failures before/after every named transaction/filesystem boundary and reopen from disk after each.
3. Check contiguous cursors, valid receipt transitions, quota equality, blob references, foreign keys, replay equivalence, and backup manifest integrity.
4. Pin algorithmic operation counts plus generous measured time/memory ceilings; report seeds on failure.

### Implementation sketch

```text
for seed in 0..<N:
  for faultPoint in FaultPoint.allCases:
    runScenario(seed, crashAt: faultPoint)
    reopenAndAssertGlobalInvariants()
```

The sketch fixes ownership and failure semantics, not exact spelling. Adapt names to compiled code without collapsing protocol, durable authority, network adapter, host execution, or client reduction into one type.

## Done when

- At least 500 deterministic scenarios and every fault point run in the normal focused check budget.
- Running the same seed twice yields identical logical database/manifest state.
- A mutation that broadcasts before commit or retries ambiguous commands goes red.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

CONTINUUM_SKIP_SURFACE_CHECKS=1 CONTINUUM_SKIP_UI_BASELINES=1 ./scripts/run-matrix.sh </dev/null

Workers run focused checks and `swift build`; the harness runs the final matrix once after independent approval. Record commands, exit codes, measured counts/limits, RED witness, restored hash, and artifact paths in `_LEDGER.md`. A real-route claim additionally requires the process/device/network observation named by this packet.

## Watch out

- Do not use random_device or wall-clock sleeps.
- Do not lower scenario count/time floors to make a slow implementation pass.
- Fuzz success does not prove backup custody or real disk-loss recovery.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
- If the packet conflicts with compiled reality or an unresolved owner decision, return `WORKER: BLOCKED <evidence>` rather than inventing a second architecture.
