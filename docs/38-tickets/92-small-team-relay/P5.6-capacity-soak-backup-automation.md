# P5.6 — Capacity Soak Backup Automation

Phase: 5 · Operations and deployment
Execution: **autonomous**
Depends on: P5.5

## Goal

Automate bounded backup scheduling, WAL checkpoint policy, capacity benchmarks, and a repeatable soak harness for the intended 100-socket small-office envelope.

## Context and design direction

Read `_DESIGN.md`, `_RUNBOOK.md`, `_DECISIONS.md`, and `_ACTION_ITEMS.md` before editing. The trusted relay is a durable small-team control/data mirror; execution hosts retain provider secrets and final authority over local resources. Class-B authenticated transcript/tool content may cross only through the typed protocol, while Class-C credentials, environment values, signing keys, raw process handles, and unrelated filesystem content remain host-only. Exactly one ticket and one fenced production/check change set belong in an iteration.

Single-node simplicity still needs measured overload behavior. The target is not infinite scale; it is explicit refusal/backpressure without corruption at the documented office load.

## Approach

1. Schedule online backup/checkpoint/compaction through injected clock and mutual exclusion; retain seven daily/four weekly by default without deleting the last known-good backup.
2. Benchmark 100 sockets, 100 events/s for ten minutes modelled/short CI sample, 1,000 events/s burst, 10,000-event cold replay, slow consumers, and concurrent backup.
3. Pin algorithmic counts plus machine-reported p50/p95/p99 commit/receipt/replay, memory, CPU, WAL/storage, refusals, and queue depth.
4. Normal matrix runs a bounded deterministic sample; full soak is an explicit artifact command on target hardware.

## Done when

- CI-sized check proves policies/invariants without real-time ten-minute sleeps.
- Target-hardware soak script records configuration and metrics and fails on corruption, gaps, unbounded growth, or limit bypass.
- Backup/checkpoint activity does not starve command receipts beyond documented ceiling.
- New behavior has deterministic positive assertions and at least one required final-code mutation witness observed red, restored byte-for-byte, then rerun green.
- Existing expectations are not changed merely to bless the implementation; RED, implementation, and GREEN evidence are recorded separately.
- No matrix leg, assertion floor, privacy boundary, authorization denial, limit, or failure case is removed or weakened.

## Watch out

- Do not tune thresholds from one lucky run.
- Do not delete retained backups before a replacement is sealed/verified.
- Performance green is not a security or physical-phone green.
- Never stage, commit, reset, clean, stash, branch, rebase, merge, push, or alter queue/loop machinery from a worker session; the harness owns those actions.
- If the packet conflicts with compiled reality or an unresolved owner decision, return `WORKER: BLOCKED <evidence>` rather than inventing a second architecture.
