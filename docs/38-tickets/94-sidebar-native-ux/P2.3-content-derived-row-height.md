# P2.3 — Content-derived row height

Phase: 2 · Row anatomy
Execution: **autonomous**
Depends on: P2.2

## Goal

Let a row's height follow the content it actually draws, so a role-less branch-less agent stops reserving thirty points of empty space.

## Context and design direction

Read `_DESIGN.md` and `_RUNBOOK.md` before editing, plus
`docs/38-tickets/91-agent-tile-ux/plan-sidebar-t3code-study.md` and
`plan-sidebar-and-state-findings.md` for the evidence this program is built on. Surface is reserved
for interaction; the row's subject is its name; one owner answers what an agent is doing; a name is
never an identifier; no stock AppKit chrome belongs in the sidebar. Every geometry assertion runs at
220, 280, and 320 pt. This ticket is deliberately scoped so another fresh agent can verify and
commit it independently.

## Approach

1. Compute row height from the lines a row will actually draw, using the existing metrics helper rather than a new constant.
2. Keep the rule explicit: height varies with content, never with how important the sidebar guesses a row is.
3. Pin the inner stack to both vertical edges, or centre it, so a shorter row has no reserved gap.
4. Assert measured height for a three-line row, a two-line row, and a one-line row, and assert that no row draws more than four points of unexplained vertical slack.

### Implementation sketch

```swift
func heightOfRow(_ row: AgentInboxRow) -> CGFloat {
    Metrics.rowHeight(for: row.variant, lines: row.drawnLineCount, insets: Inset.card)
}
```

The sketch establishes ownership and direction; adapt names to the compiled code, but do not replace
the architecture with a shortcut that couples derivation, presentation, and persistence.

## Done when

- A role-less, branch-less row measures shorter than a full row, and neither carries unexplained slack.
- Height is a function of drawn content only; no branch of the calculation reads state, attention, or lifecycle importance.
- Measured heights are asserted for one-, two-, and three-line rows at all three widths.
- Scroll position and selection survive a height change caused by content arriving.
- Relevant new behavior has a deterministic positive assertion and at least one required negative
  witness observed red against the final check.
- No existing matrix leg, assertion floor, contrast requirement, or I5 boundary is weakened.

## Watch out

**Carried findings from the 2026-08-04 stall (three review rounds, independent reviewer).** The
attempt reached the rework limit; two of the three final findings are real and are yours to close.
The third was a runbook contradiction about baselines, now resolved in `_RUNBOOK.md` — read the
"ticket that legitimately moves a baseline" section before you run any visual leg.

- **Width invalidation must not have a dead band.** A previous candidate skipped width changes of
  0.5 pt or less. Measured-fit tier boundaries are exact and AppKit widths are fractional, so a cell
  can cross a tier while the table keeps the old height, which clips or leaves slack. Invalidate on
  any width change that can change a tier, and exercise a **fractional** divider move, not only a
  large jump.
- **The row-height cache must be invalidated by the resize path, not only by `applyRows`.** Re-tiering
  happens in `layout()` as the divider moves; `noteHeightOfRows` was only reachable from
  `applyRows`, so a row kept its old height after its band appeared or vanished. Drive a **live width
  transition** on one host rather than building a fresh host per width — a fresh host per width cannot
  observe a stale cache at all, which is why the first attempts read green.
- **Scroll restoration must not double-apply its delta.** Storing document-space Y and adding the
  delta to the post-layout origin double-counts when AppKit has already constrained the origin, e.g.
  at the bottom when a row shrinks. Assert the **visible anchor**, and cover a shrink at the bottom
  as well as growth mid-list.
- **Prove the height actually changed.** An earlier witness asserted selection and scroll offset but
  never that the row moved from one height to the other, so deleting the invalidation call left it
  green. Assert the before and after heights by value, at all three widths.
- **Choose a row the growth can actually disturb.** `InboxSort` orders active fixtures newest-first,
  so the last fixture sits below a short viewport and its growth proves nothing about scroll
  position. Use a visible or preceding row.
- **Derivation and presentation must agree on empty strings.** The line count treated `role: ""` as
  absent while the meta text used `compactMap` without filtering empties, so such a row rendered
  `" · "` in a visible band while being counted as having no detail line. Both public initializers
  accept empty strings, so this is reachable.


- `heightOfRow` currently refuses content-varied height by design; changing that is the point of this packet, and the pinned 79 pt assertions were un-pinned in P0.4.
- Variable heights plus row reuse can desynchronise the list's height cache; invalidate it explicitly when content changes.
- Do not make height depend on importance — that is the density rule this program locked.
