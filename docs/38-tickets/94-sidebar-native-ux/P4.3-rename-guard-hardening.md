# P4.3 — Rename hardening and the compare-and-swap guard

Phase: 4 · Identity and naming
Execution: **autonomous**
Depends on: P4.2

## Goal

Make a human's rename unloseable: inline editing that behaves, and a guard that stops any late automatic name from overwriting it.

## Context and design direction

Read `_DESIGN.md` and `_RUNBOOK.md` before editing, plus
`docs/38-tickets/91-agent-tile-ux/plan-sidebar-t3code-study.md` and

## Approach

1. Harden inline rename: double-click the row body only — bail on modifier keys, bail if already editing, bail if the click came from a nested control — with Return committing, Escape cancelling, and blur committing behind a did-commit flag so blur after Return cannot double-fire.
2. Suppress the trailing click of a double-click so entering rename does not also activate the row.
3. Add an in-flight naming marker plus a compare-and-swap: an automatic name lands only if the marker is still current and the name is still what it was when generation began.
4. Make a manual rename disarm any pending generation, and reject a request that carries both an explicit name and a regenerate intent.

### Implementation sketch

```swift
struct NamingRequest { let id: UUID; let expectedName: String }
func applyGeneratedName(_ name: String, for request: NamingRequest) {
    guard record.namingRequest?.id == request.id,
          record.displayName == request.expectedName else { return }   // CAS
    record.displayName = name
}
```

The sketch establishes ownership and direction; adapt names to the compiled code, but do not replace
the architecture with a shortcut that couples derivation, presentation, and persistence.

## Done when

- A rename committed during a pending generation survives it, asserted by a test that lands the generated name after the rename.
- Return commits, Escape reverts, blur commits exactly once, and an empty name abandons the edit without dispatching.
- A double-click enters rename without activating the row.
- A request carrying both a name and a regenerate intent is rejected.
- Relevant new behavior has a deterministic positive assertion and at least one required negative
  witness observed red against the final check.
- No existing matrix leg, assertion floor, contrast requirement, or I5 boundary is weakened.

## Watch out

- Checking the request id only before starting generation closes the wrong window; the reference implementation shipped exactly that bug. Check on the way out.
- Blur-after-Return double-commits without a did-commit flag.
- An empty name must not silently revert to a generated one, and must not re-trigger generation.
- Never stage, commit, push, rebase, or alter queue/loop machinery outside the per-ticket workflow.
- If the packet conflicts with compiled reality or a locked decision, mark it `blocked` with concrete
  evidence; do not improvise a second architecture.
