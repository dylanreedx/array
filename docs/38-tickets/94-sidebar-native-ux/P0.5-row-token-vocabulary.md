# P0.5 — Row surface, line, and width token vocabulary

Phase: 0 · Foundations
Execution: **autonomous**
Depends on: P0.1

## Goal

Give the sidebar the semantic surface and line roles plus the single named hairline-width token it will consume, without adopting any of them in a live view.

## Context and design direction

Read `_DESIGN.md` and `_RUNBOOK.md` before editing, plus
`docs/38-tickets/91-agent-tile-ux/plan-sidebar-t3code-study.md` and
`plan-sidebar-and-state-findings.md` for the evidence this program is built on. Surface is reserved
for interaction; the row's subject is its name; one owner answers what an agent is doing; a name is
never an identifier; no stock AppKit chrome belongs in the sidebar. Every geometry assertion runs at
220, 280, and 320 pt. This ticket is deliberately scoped so another fresh agent can verify and
commit it independently.

## Approach

1. Extend the token layer additively with any sidebar role it still lacks, reusing existing token values rather than inventing colours.
2. Add the named hairline width token that `docs/38-tickets/93-global-border-audit.md` will sweep the app with, and state in a comment that the sidebar is its first consumer.
3. Gate the interaction ladder by measurement: selection quieter than hover, hover perceptible against the resting surface, and every gated role clearing its contrast floor in both appearances.
4. Adopt nothing in a view, so no baseline can move in this packet.

### Implementation sketch

```swift
enum AgentSurfaceRole { case rowBase, rowHover, rowSelected, rowActive }
enum SidebarMetrics { static let hairline: CGFloat = 0.5 }  // ticket 93's shared width
```

The sketch establishes ownership and direction; adapt names to the compiled code, but do not replace
the architecture with a shortcut that couples derivation, presentation, and persistence.

## Done when

- The ladder is asserted by measured contrast, not by naming: an inverted hover/selected pair is red.
- The width token is a single declaration both the sidebar and ticket 93 can consume.
- No live view references the new roles yet, and every baseline is byte-identical.
- Existing pinned token counts and contrast tables are unchanged.
- Relevant new behavior has a deterministic positive assertion and at least one required negative
  witness observed red against the final check.
- No existing matrix leg, assertion floor, contrast requirement, or I5 boundary is weakened.

## Watch out

- Where an existing check pins a token count, add a new type rather than a new enum case; growing a pinned enum forces this packet to renumber gates it may not touch.
- A fill is not a state indicator — keep the row-emphasis floors low and leave whether they read correctly to P1.5.
- Do not sweep borders outside the sidebar; ticket 93 owns that.
- Never stage, commit, push, rebase, or alter queue/loop machinery outside the per-ticket workflow.
- If the packet conflicts with compiled reality or a locked decision, mark it `blocked` with concrete
  evidence; do not improvise a second architecture.
