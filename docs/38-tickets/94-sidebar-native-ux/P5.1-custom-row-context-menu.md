# P5.1 — Custom context menu for an agent row

Phase: 5 · Native interaction
Execution: **autonomous**
Depends on: P4.3

## Goal

Replace the stock right-click menu with a Continuum control from the tile's choice family, offering only actions the runtime can honour.

## Context and design direction

Read `_DESIGN.md` and `_RUNBOOK.md` before editing, plus
`docs/38-tickets/91-agent-tile-ux/plan-sidebar-t3code-study.md` and
`plan-sidebar-and-state-findings.md` for the evidence this program is built on. Surface is reserved
for interaction; the row's subject is its name; one owner answers what an agent is doing; a name is
never an identifier; no stock AppKit chrome belongs in the sidebar. Every geometry assertion runs at
220, 280, and 320 pt. This ticket is deliberately scoped so another fresh agent can verify and
commit it independently.

## Approach

1. Present a custom menu built from the tile's `ChoiceListView`/`ChoicePopoverController` family on right-click and on Control-click, anchored at the click point and clamped to the screen.
2. Populate it from the row's real capabilities — open, rename, settle or un-settle, snooze, stop, reveal worktree, archive, delete — hiding rather than disabling anything the runtime cannot honour, and mark the destructive items.
3. Support the full keyboard contract: arrow traversal, type-select, Return to activate, Escape to dismiss, focus returned to the row, and VoiceOver announcement of the menu and its items.
4. Make right-click select the row it targets without disturbing an existing multi-selection that already contains it, and assert that no stock `NSMenu` is presented from the sidebar.

### Implementation sketch

```swift
override func rightMouseDown(with event: NSEvent) {
    let target = row(at: convert(event.locationInWindow, from: nil))
    selectForContextMenu(target)
    ChoicePopoverController.present(items: menuItems(for: target),
                                    at: event.locationInWindow, in: self)
}
```

The sketch establishes ownership and direction; adapt names to the compiled code, but do not replace
the architecture with a shortcut that couples derivation, presentation, and persistence.

## Done when

- Right-click and Control-click both present the custom menu; no stock `NSMenu` is presented anywhere in the sidebar, asserted structurally.
- Items are derived from capabilities: an action the runtime cannot honour is absent, not greyed.
- Keyboard traversal, type-select, Return, and Escape all work, and focus returns to the originating row.
- Right-clicking a row inside an existing multi-selection preserves that selection; right-clicking outside it retargets.
- Relevant new behavior has a deterministic positive assertion and at least one required negative
  witness observed red against the final check.
- No existing matrix leg, assertion floor, contrast requirement, or I5 boundary is weakened.

## Watch out

- A menu that mutates the selection out from under a bulk action is how a destructive command hits the wrong rows.
- Screen-edge clamping matters at 220 pt — the menu is wider than the sidebar.
- Do not reimplement the choice family here; reuse it, and keep changes to it presentation-only.
- Never stage, commit, push, rebase, or alter queue/loop machinery outside the per-ticket workflow.
- If the packet conflicts with compiled reality or a locked decision, mark it `blocked` with concrete
  evidence; do not improvise a second architecture.
