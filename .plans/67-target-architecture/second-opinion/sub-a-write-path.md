# Sub-A: write path at `array/integration` / `1451c030`

This is a static source audit. I did not execute Array, checks, a build, or any write in the repository. Quotations below are from HEAD. The initial reading order was `CLAUDE.md`, consolidated architecture, board export, then all fifteen `s1`–`s11`/`o1`–`o4` reports. The reports' empirical claims about production files were not independently checked because the owner forbade touching that state.

## Verdict on ARC-1's diagnosis

**Confirmed, with important incompleteness.** `WorkspaceRuntime` lazily creates `armingSaveController` with the then-current `workspaceId` (`WorkspaceRuntime.swift:422-427`: `if armingSaveController == nil ... WorkspaceStore(workspaceId: workspaceId...)`). `switchWorkspace` changes `workspaceId` and `document` (`:1616-1618`) without rebinding that controller. It is drained on departure (`:798-808`) but survives. `WorkspaceDocumentSaveController` retains `pendingDocument = document` and its store (`WorkspaceDocumentSaveController.swift:23-26,39-49`), so an arm in B after first arming in A writes a snapshot of B into A's document file (`:54-64`). This is a deterministic code path, not proof that any specific production corruption came from it. The first pass's reported prod-file examples are unverified here.

**Confirmed, with a clean-exit qualification.** A debounced arm captures a value snapshot (`WorkspaceDocumentSaveController.swift:39-49`). An immediate save constructs a *new* controller (`WorkspaceRuntime.swift:1433-1445`), so that new controller does not supersede the pending arm. Its later timer can overwrite the immediate save. A clean workspace departure subsequently calls `persistDepartingWorkspaceState` and writes the live document (`WorkspaceRuntime.swift:1493-1495,1861-1885`), which may repair the disk. A crash, or a disk-reading writer before departure, can preserve and re-import the older state. The timer callback uses `try?` (`WorkspaceDocumentSaveController.swift:48-49`), and the runtime drains with `try?` (`WorkspaceRuntime.swift:481-484,805-807`); a failed arm save is therefore invisible to the caller.

**Confirmed.** `persistLayoutTransaction` begins with `var document = try store.load()` (`ContinuumApp.swift:14663-14677`), mutates that disk snapshot, saves it, and calls `workspaceRuntime?.replaceDocument(document, for: workspaceId)` (`:14732-14745`). Yet `commitZonePlacement` states that `runtime.document` is live truth and forbids reload (`WorkspaceRuntime.swift:105-113`). `persistLastExplicitCreationScope` also loads disk and copies it into the runtime (`ContinuumApp.swift:14952-14966`). The board's phrase “six AppDelegate writers do disk load → partial mutate → save → replaceDocument” overstates the mounted case: four zone callbacks first use runtime commit and return; their disk fallbacks execute only without a runtime (`ContinuumApp.swift:14539-14549,14580-14590,14622-14631,14755-14766`). The layout transaction and explicit-creation-scope paths *do* reload while mounted. Those two are enough to break the one-owner claim.

**Registry ownership is duplicated.** `ProjectEntry.workspaceId` and `WorkspaceEntry.projectIds` both record ownership (`Registry.swift:307-320,330-351`). `exclusiveWorkspaceOwner` gives the project declaration precedence in some disagreement cases (`:145-171`), and `assignProject` updates both (`:176-195`). Deleting a workspace uses both to clear project ownership (`:227-242`). One canonical field plus a derived index is sound, but migration must account for inconsistent historical data, including an unowned project still listed by a workspace.

## Writers and read paths

The persistent workspace document is `WorkspaceDocument` v9 with no embedded `workspaceId` (`WorkspaceDocument.swift:3-22,248-253`); `WorkspaceStore` selects the file path with the constructor id and writes any document passed to it (`WorkspaceStore.swift:3-22,29-50,62-69`). Production workspace-document saves include: runtime `commitZonePlacement`, `commitCreatedZone`, `commitClosedZone` (`WorkspaceRuntime.swift:108-153`); `setActiveZone` immediate or debounced (`:363-429`); `ensureZone` (`:591-615`); `addProjectZone`'s extra fresh controller (`:873-929`); runtime helpers calling `persistWorkspaceDocument` (`:307,613,1153,1386,1415`); switch/quit departing save (`:798-808,1861-1885`); four AppDelegate fallback zone writers (`ContinuumApp.swift:14539-14656,14755-14793`); the live layout transaction (`:14663-14745`); and last explicit scope (`:14952-14966`). The exact call graph of every runtime helper should be mechanically audited when centralizing; this list enumerates direct save sites in the relevant production region.

There are **at least three categories of save-controller instances**: one long-lived ambient-arming controller (`WorkspaceRuntime.swift:347,422-427`); a fresh controller per ordinary synchronous runtime save (`:1433-1445`) plus a separate one in `_addProjectZone` (`:924-929`); and fresh controllers in six AppDelegate disk writers (`ContinuumApp.swift:14569,14609,14650,14732,14785,14963`). The save controller has no file identity check and no coordinator shared between instances (`WorkspaceDocumentSaveController.swift:21-35,54-70`). I excluded check-fixture instances.

Mounted disk-to-memory paths: `persistLayoutTransaction` and `persistLastExplicitCreationScope` reload full documents and invoke `replaceDocument` as above; `presentProjectHomePicker` reads the persisted document for recent scope instead of `workspaceRuntime.document` (`ContinuumApp.swift:14848-14858`). That picker read is a display source; it will lag a pending arm or other in-memory mutation. The four fallback zone writers can load disk if called before runtime installation. Expected boundary reads are boot and `switchWorkspace` (`WorkspaceRuntime.swift:1425-1430,1466-1486`). Project canvases are also re-read while mounted: zone membership repair (`:507-541`), `ensureZone` (`:591-613`), adding a project zone (`:876-888`), project saves (`ZoneRuntimeController.swift:660-667`), spawn persistence (`TileSpawner.swift:2423-2440`), layout transaction (`ContinuumApp.swift:14703-14723`), and focus restore/departure (`WorkspaceRuntime.swift:1875-1882,1889-1900`). These project reads are not inherently wrong; the problem is merging a stale disk image with a different live owner without ordering or generation checks.

The board undercounts `canvas.json` writers. The `ZoneRuntimeController` queue handles only its own async and sync saves (`ZoneRuntimeController.swift:680-700,735-746`). Outside that queue, production directly writes project canvases in membership repair (`WorkspaceRuntime.swift:525-541`), departure focus (`:1875-1882`), browser inspector reveal/refresh (`TileSpawner.swift:1171-1175,1260-1265`), boot note-id migration (`:2080-2099`), note conversion (`:2140-2145,2225-2234`), spawn persistence (`:2415-2441`) and run-artifact spawn (`:2452-2481`), browser-profile deletion (`ContinuumApp.swift:14118-14127`), layout transaction and its rollback (`:14703-14740`), boot walk (`:16256-16278`), and diff-review spawn (`:16625-16644`). The latter direct writes are not ordered against the queued snapshot; one serial queue around three named writers would leave numerous bypasses. Some are flat-scene writers and must disappear or migrate with ARC-2. `TileSpawner.persistCanvasForCurrentModel` explicitly does `state.tiles = tiles` for a single zone (`TileSpawner.swift:2225-2233`), an erasure risk for a project with multiple zones or deferred tiles; this is outside the board's named flat fallback.

## Mechanisms missing from the board

1. **A queued older canvas snapshot can land after a newer direct write.** `flushCanvasSaveOffMain` takes a snapshot, sets `isCanvasDirty = false`, queues a `try? store.saveCanvas(snapshot)`, and reports `onCanvasStatePersisted` unconditionally (`ZoneRuntimeController.swift:690-700`). A later `persistLayoutTransaction` writes the same file directly on the main thread (`ContinuumApp.swift:14726-14734`); queued work can finish afterward and replace it. This ordering is an inference from independent queues, not a measured schedule. The app's `canvasSaveQueue.sync` only orders the controller's own synchronous flush (`ZoneRuntimeController.swift:735-745`), and `flushAll` does not wait for a previously queued task when `isCanvasDirty` was cleared (`WorkspaceRuntime.swift:788-807`). A successful callback after a failed `try?` is a verified false acknowledgment.

2. **Whole-scene writes exist in ancillary features.** Browser inspector actions call `saveCanvas(canvasView.canvasState)` (`TileSpawner.swift:1171-1175,1260-1265`), browser-profile delete edits and saves a `canvasView.canvasState` snapshot (`ContinuumApp.swift:14118-14127`), and note conversion's zone path replaces the full persisted `tiles` array with one zone's tiles (`TileSpawner.swift:2225-2233`). Hazard 9 says `canvasState` may hold the departed project's flat tiles after layering; these sites can undo the merge-safe persistence rule even if the main spawn writer is corrected. The note path is worse: `tiles(inZone:)` returns `layer.tiles` (`CanvasNSView.swift:6469-6474`), whose frames were converted WORLD→ZONE-LOCAL on installation (`WorkspaceRuntime.swift:1562-1572`), and `persistCanvasForCurrentModel` writes those local frames verbatim as `state.tiles` (`TileSpawner.swift:2225-2233`). Thus note reuse in a nonzero-origin zone can persist a shifted frame **and** erase sibling-zone tiles. The path is reached from `convertNoteToDocument` after finding an existing file (`TileSpawner.swift:2125-2145`). This refutes the first pass's broad claim that frame-space conversion holds on every live write path; it verified only the main save paths.

3. **Registry and document commit order has no cross-file transaction.** `commitCreatedZone` assigns ownership and saves the registry before it appends and saves the zone (`WorkspaceRuntime.swift:116-135`); the picker does the same before `commitProvisionalZone` (`ContinuumApp.swift:14884-14935`); `addProjectZone` also commits the registry before runtime creation (`ContinuumApp.swift:15340-15355`). If the second write fails, the project may appear owned without a zone. Conversely, `commitCreatedZone` mutates `document` before its save and does not roll the mutation back on failure (`WorkspaceRuntime.swift:132-135`), while the canvas callback logs and returns (`ContinuumApp.swift:14580-14587`). These are verified partial-commit paths. A single owner of only `WorkspaceDocument` does not make registry + document + project canvas atomic.

4. **A picker action can cross a workspace boundary.** The picker closure captures `placement` and `canvasView` at presentation (`ContinuumApp.swift:14832-14875`), but reads `self.workspaceRuntime?.workspaceId` only on confirmation (`:14876-14883`) and then commits to the captured `placement.zoneId` (`:14919-14939`). Switch entry points call `workspaceRuntime.switchWorkspace` without dismissing this picker (`ContinuumApp.swift:10544-10555,15329-15337`). If AppKit allows confirmation after switch, the result can target a stale zone or assign a project to the new workspace before that zone commit fails. This is an inferred interaction schedule, not a reproduced UI result. Capture a workspace/session epoch with the picker, cancel on switch, and make every async callback check it before modifying any store.

5. **Identity checks alone do not protect files across two processes.** `WorkspaceStore.save` lacks identity today (`WorkspaceStore.swift:62-64`); adding it protects the workspace document file. Project `canvas.json` remains shared between prod and dev channels by root (CLAUDE.md hazards 9–10), and `ProjectStore.saveCanvas` has no compare-and-swap or channel id (`ProjectStore.swift:100-115,137-155`). The exclusive project lock may prevent ordinary concurrent use, but a queued write after controller release or a code path bypassing the controller needs a witness. ARC-1's save pipeline must fence both project identity and controller lifetime, and must not claim channel isolation for `.array/`.

6. **The proposed quarantine adds a second durable zone location.** ARC-1 suggests `quarantinedZones` in the document. The existing mount boundary already filters foreign zones while preserving them in `document.zones` (`WorkspaceRuntime.swift:1672-1686,1861-1867`). A second field introduces migration and merge questions: what if registry ownership changes while a zone is quarantined, or duplicate `zoneId`s appear in both arrays? Prefer one persisted zone collection with a derived read-only quarantine view, with explicit repair operations. More urgent: `reconcileHydration` still plans over `document.zones` and iterates raw zones (`WorkspaceRuntime.swift:1774-1802`), so the derived mounted-zone boundary must apply at every acquisition, not just initial materialization. This gap appears in `s11`, but is absent from the board's ARC-1 mechanism.

7. **Zone scope mixes a creation default with persistence ownership.** `setZoneScope` says existing member tiles are intentionally untouched (`CanvasNSView.swift:1014-1015`), yet changes the zone layer's `placement.projectId` (`:1022-1031`). Project persistence selects entire layers by that *new* project id (`CanvasNSView.swift:6580-6589,6600-6610`), while merge coverage likewise uses the installed layer id (`:6663-6687`). If a populated zone changes from project A to B, existing A tiles can be serialized into B's `canvas.json`, while A's file retains its old copies; a remount's membership logic reads each project's own file (`WorkspaceRuntime.swift:500-523`) and may duplicate or misplace them. This is an inferred outcome from the verified selectors, not a run. The model must separate a zone's default project for **new** tiles from each tile's immutable project storage owner; changing Home should not transfer existing tiles or retag a layer's backing store. This is a larger architectural fault than the first pass's save-controller race.

## Architectural recommendation

Use a **main-actor mounted session with an identity-fenced, per-store commit coordinator**, rather than a generic event log or CRDT retrofit. A session owns `workspaceId`, `document`, registry snapshot/revision, and a monotonic scene generation. All workspace mutations produce a new document value from the current one and hand that generation to one debounced/immediate saver. The saver writes the latest value under the same session id and acknowledges only after success. Every canvas mutation uses a project-specific serial writer with generation checks; no direct `ProjectStore.saveCanvas` from AppDelegate, spawner, or boot code after mounting. Keep world frames on disk and zone-local frames inside layers, with conversion at the boundary. Encode `workspaceId` in v10 documents and reject a mismatch on read and write. Attach an epoch to picker and other deferred UI closures; reject them after switch.

The coordinator must define multi-file ordering. For create-zone, a registry assignment and document zone must either be a recoverable intent with a completion record, or have a rollback/reconciliation rule if either write fails. For a layout transaction touching workspace and several project canvases, the existing manual rollback (`ContinuumApp.swift:14726-14740`) is best-effort: rollback can fail, as its catch already logs. A small write-ahead intent for **only** these multi-file operations is more valuable than an event log for every gesture. On next mount, inspect and finish or reverse the intent before rendering. This costs more than ARC-1's claimed ~200 lines, but solves the actual cross-file consistency boundary.

An actor could make ordering explicit if storage leaves the main actor, but AppKit scene snapshots and callbacks are main-actor-bound (`WorkspaceDocumentSaveController.swift:21-22`, `ZoneRuntimeController.swift:690-700`). Introducing an actor now adds async seams at gesture and quit, while it does not by itself solve multi-file atomicity or stale snapshot ownership. An append-only event log would provide replay and auditability but adds schema/version and compaction complexity across registry, workspace, and project files. `ambientTiles`' LWW `zoneId` register is one field (`WorkspaceDocument.swift:3-5,23-26`), not a general CRDT for zone geometry, names, files, and project ownership; expanding it would add conflict semantics without addressing local single-process ordering. All three are disproportionate for the current failure mode.

ARC-1 survives as the first protective step, but its scope and estimate must change: enumerate and route every direct canvas writer, fence deferred callbacks, and specify failure handling for registry/document/project writes. The earliest shippable slice is workspace identity + re-bound saver + no mounted full-document reload, with a two-workspace arming and stale-snapshot outcome witness. Canvas writer consolidation and multi-file recovery can follow in separately witnessed slices. A seeded random harness is useful afterward; deterministic directed schedules (hold the canvas queue, fail the second file write, switch while a picker is open, fail the timer write) are necessary to prove the difficult races.
