# Sub-B independent scene and tile review

Model: gpt-6-sol (as assigned); reasoning effort: medium insofar as visible to this agent. Read-only review of `array/integration` at `1451c030e3ca0987b31de5b524b7411e9cc61cf8` on 2026-09-27/28. Conclusions below are static code findings or explicitly marked inferences. No app launch, build, check flag, test, Git mutation, or project/app data access was performed.

## Verdict

The board's central scene diagnosis is supported. The mounted document can show a zone header without a `ZoneLayer`; it can acquire a controller for that zone later without creating its layer. `installProjectTile` then silently installs in the flat collection, even after the flat scene has been retired. Existing view swaps also run spawn geometry, so browser tier changes and other materialization can settle unrelated members. The proposed single scene graph is the right direction, provided it distinguishes **model completeness** (all mounted zones and persisted tiles have scene nodes) from **view/runtime residency** (NSViews and terminals/WebViews can be evicted).

The highest priority additional design gap is how to populate cold project nodes. Current `membership(forProject:)` reads `controller.projectStore`, while mount creates controllers only for live zones (`WorkspaceRuntime.swift:496-548,686-702`). ARC-2 cannot assert that every cold zone has every persisted tile until it introduces a read path for project canvas data independent of live runtime acquisition, or changes controller ownership and proves the budget still governs only processes. An unavailable or locked project also needs an explicit scene status, not an empty layer that persistence interprets as deletion.

**Critical schema distinction missed by the board:** a zone's `projectId` is a *future creation scope*, while its existing members can keep a different filesystem owner. `setZoneScope` says so explicitly and changes `layer.placement.projectId` without changing tile records (`CanvasNSView.swift:1014-1040`). Yet `tilesInWorldFrames(forProjectId:)` and `installedZoneIds(forProjectId:)` infer persistence ownership solely from that mutable layer project id (`:6600-6611,6634-6635`). If a populated zone is rebound from A to B, the layer's old A members now appear in B's persistence projection, even though a tile may still carry `filesystemProjectId == A` (`CanvasState.swift:288-294`). The A projection loses that layer and its merge leaves the old A records on disk; B's next save can copy the same tile ids into B's canvas. On remount, membership is rebuilt from each scoped project's store (`WorkspaceRuntime.swift:496-548`), so the view can change abruptly. The picker permits choosing another project in the same workspace and then calls `setZoneScope` (`ContinuumApp.swift:14875-14938`). This is a static, reachable path; I did not run a reproduction. The scene graph must represent zone creation scope separately from each tile's durable owner/store. Any cross-project move must be a deliberate transfer transaction, never an implicit consequence of editing a zone header.

## Confirmed mechanisms

1. **Chrome without members.** `WorkspaceRuntime.install` and `switchWorkspace` skip project-layer construction unless `plan.tier(...) == .live` (`WorkspaceRuntime.swift:686-702,1539-1548`). Both pass *all* mountable zones as `documentZones` to `setZones` (`:767-770,1596-1599`); `setZones` builds `liveZones`, render models, and chrome from those zones but `zoneLayers` only from the supplied layer list (`CanvasNSView.swift:6232-6292`). `setActiveZone` acquires a missing project controller but does not install a layer (`WorkspaceRuntime.swift:363-430`); `reconcileHydration` similarly changes controller/tier without installing one (`:1758-1816`). Thus panning or clicking cannot complete the half-mounted scene. This is a code certainty, independent of a wake hypothesis.

2. **Flat fallback after retirement.** A layer miss enters `install(tileView:for:)` and returns `.flatCanvasState` (`CanvasNSView.swift:6805-6823`). The persisted-workspace boot explicitly calls `retireFlatCompatibilityScene` before mount (`ContinuumApp.swift:16209`; `CanvasNSView.swift:6305-6323`), and `allTilesInWorldFrames`/`tileRecord` exclude flat tiles after retirement (`CanvasNSView.swift:6550-6575`). `TileSpawner.persistProjectCanvas` nevertheless writes the flat `canvasState` directly for that return value (`TileSpawner.swift:2415-2423`). This can create an installed-but-undiscoverable tile and overwrite that project's canvas with a stale flat snapshot. The precise resulting bytes depend on the active spawner/store and preceding canvas contents; the source alone establishes the unsafe path, not an observed production loss.

3. **Seventeen installs, mixed meanings.** I confirmed all 17 `installProjectTile` call sites in `TileSpawner.swift`: true creates at 325, 950, 1034, 1216, 1586, 2021, 2071, 2382; view replacement/restore at 646, 1071, 1123, 1253, 1481, 2167, 2191, 6250, 6263. The method always calls `growZoneOnSpawn` and `arrangeAutoLayoutAfterSpawn` after replacing or appending the tile (`CanvasNSView.swift:6805-6850`). The latter expands then settles the whole zone and commits geometry (`:829-845`). Phase B suppresses auto layout for its own restart loop (`ContinuumApp.swift:16496-16523`), but budget enforcement runs after the suppression block (`:16525`) and calls browser snapshot installation (`WorkspaceRuntime.swift:1708-1724`). This directly supports drift from non-user view changes. The source establishes a mover; the size/frequency of visible drift remains an inference without a behavioral run.

4. **Two direct stale spawns remain.** `spawnRunArtifacts` computes placement and z-order from `canvasState.tiles`, calls `install`, and saves `canvasState` (`TileSpawner.swift:2453-2482`). `spawnDiffReviewFromPalette` does the same (`ContinuumApp.swift:16623-16650`). The boot-only `installInitial*` walk is a separate legacy path, per `ContinuumApp.swift:16227-16254`; it should become import/migration logic before the mounted graph is constructed. `makeProjectTilePlacement` still includes its flat branch (`TileSpawner.swift:7884-7947`), so removing the flat scene must also make zone resolution a typed precondition, including for child browser windows whose opener zone may differ from the armed zone.

5. **Jelly cannot carry members of a ghost.** `autoLayoutScene` combines every `liveZone` with tiles only from installed layers (plus active flat tiles) (`CanvasNSView.swift:437-457`). `resolveOuterCollisions` considers all zones and translates only scene tiles stamped with a pushed zone (`CanvasAutoLayoutEngine.swift:888-933`). A layerless zone is a peer with no members in that solve; moving it can leave its world-frame persisted tiles behind. The exact persistence path must be exercised to prove a particular after-relaunch outcome, but the omitted members are visible in the constructed scene.

6. **Membership repair does not ensure containment.** A tile stamped to an owned project zone is accepted without examining its frame; nil or foreign-in-document stamps are assigned to a containing zone or the home zone even when no project zone contains the tile (`ZoneMembershipRepair.swift:51-96`). The repair writes a new stamp with the world frame unchanged (`WorkspaceRuntime.swift:514-548`). Layer tile moves cannot enter the older `reevaluateZoneMembership`, whose first guard searches only `canvasState.tiles` (`CanvasNSView.swift:1981-1987`). This violates a proposed `membership == geometric containment` invariant at mount even if all layers exist.

7. **Growth and authoritative placement diverge.** `growZoneToFitMembers` writes only `liveZones` (`CanvasNSView.swift:1954-1979`), whereas `allZonePlacements` prefers a layer's placement (`:2570-2583`). `expandZoneToContainMembers` and grow-on-spawn do not invoke the outer collision solver (`:847-875,1943-1949`); resize-pressure returns before it too (`CanvasAutoLayoutEngine.swift:130-165`). User-decided policy is growth pushes neighbours like drag and never overlaps. Each growth path must route through the same placement transaction and outer collision solver, with moved peers and their members committed atomically.

8. **Bare tiles have no mounted home.** `WorkspaceDocument.ambientTiles` explicitly permits formerly zoned ambient tiles with `zoneId == nil` (`WorkspaceDocument.swift:23-27`), while the runtime builds ambient layers only for document zones (`WorkspaceRuntime.swift:680-685,1540-1544`). The close-zone keep-tiles path calls `setTileZone(id,nil)` and removes the zone's live chrome (`CanvasNSView.swift:2104-2117`); `setTileZone` updates the membership cache and a flat `canvasState.tiles` record only (`:317-326`). It does not update a layer tile's stamp or move the tile to a root scene collection. In the layered path a nonempty removed zone layer can remain installed after chrome removal. This is another reason that “every zone has a layer” is insufficient: the graph needs an explicit root for unzoned project and ambient tiles, plus a membership move that updates model, view ownership, and persistence together. The exact user-visible outcome of close-and-remount is unverified here.

## Additional seams the architecture should specify

- **Cold data acquisition and failure status.** Build the scene model from the workspace document plus each owned project's persisted canvas before deciding runtime tier. The present `ZoneRuntimeController` provides that canvas read (`WorkspaceRuntime.swift:496-505`), but controller acquisition is tied to `.live` and can fail (`:1788-1809`). An all-zone graph requires a non-runtime project snapshot reader or a changed controller lifecycle. If a read fails, preserve the last known tile ids/coverage as unresolved and refuse geometry or destructive persistence for that zone. An empty loaded layer is a valid empty zone; a failed read is not.
- **Tier scope mismatch.** Hydration plan tiers are per zone (`ZoneHydrationOrchestrator.swift:38-103`), while `ZoneRuntimeController.hydrationTier` is per project (`ZoneRuntimeController.swift:80,553-567`). `reconcileHydration` iterates zones and calls `setTier` on the shared project controller (`WorkspaceRuntime.swift:1788-1814`). A project can intentionally have several zones (`CanvasNSView.swift:6578-6585`); differing zone tiers then compete over one controller state. This is a static inference of last-processed-zone behavior and warrants a two-zones-one-project witness. Scene nodes should be per zone; process/runtime residency should be keyed by tile or aggregated by project with a defined reduction, never assigned by each zone in sequence.
- **Replacement lifecycle.** `setZones` calls `prepareForRemovalFromScene` on old tile views (`CanvasNSView.swift:6232-6245`). `installProjectTile` replaces an existing view with unregister/remove only (`:6825-6831`). A new `materialize` API must establish a single teardown and handoff contract, including focus broker, surface residency, observers, runtime identity, and tile record replacement. `materialize` must not mutate frame, zone membership, z-order, or persistence; runtime state changes can persist through their own store.
- **Identity and frame ownership.** `autoLayoutScene` and transaction application choose first occurrences of duplicate tile UUIDs (`CanvasNSView.swift:437-452,580-597`). A unified graph should key a tile by `(projectId, tileId)` or assert global UUID uniqueness at import and mutation. It should store one canonical WORLD frame in the scene model, with zone-local geometry derived only at a view boundary; the current persistent `canvas.json` WORLD convention and `memberTiles` WORLD→local conversion (`WorkspaceRuntime.swift:1552-1572`) must be preserved during migration.
- **Scope versus store.** Zone `projectId` currently does two incompatible jobs: creation default and filter for loading/saving member tiles. The picker advertises that a scope change affects *future* filesystem tiles (`ContinuumApp.swift:14931-14938`), so the persistence projection must group tiles by each tile's owning project, independent of its current visual zone. A project canvas can then hold tiles in zones scoped to other projects, and mount must resolve those without treating the stamp as corrupt or foreign. This requires an explicit tile owner for every tile kind, with migration for older records that lack one.
- **Root scene membership.** Give unzoned tiles a first-class canvas root under the workspace scene, separate from any `ZoneLayer`. Closing a zone with “keep tiles” becomes an atomic reparent of its members to that root with unchanged WORLD frames and unchanged store owner. Closing with deletion removes the records and views through one path. This avoids dangling layers and makes the ambient `zoneId == nil` format renderable.
- **Commit boundary.** A geometry transaction that pushes zones may affect the workspace document and multiple project `canvas.json` files. Current code can commit each store separately; a provenance label alone does not make the gesture atomic across files. Define prepare/validate/apply/commit with an action id and rollback or recovery journal. Validate mounted membership, containment, non-overlap, and unchanged-by-system frames against the full scene **before** any writer sees a partial solve. The action should carry the user gesture (including spawn and growth), agent grant, or system materialization reason. Mount-time repair should be an explicit migration/recovery transaction, not silently classified as an idle system movement.
- **Meaning of no overlap.** The current solver has a bounded push loop (`CanvasAutoLayoutEngine.swift:934-947`) and works with a preferred gap; the invariant must inspect the final result even if the iteration bound is reached. Define whether group zones and bare tiles participate (the solver includes every zone and bare tile as peers, `:888-890`). The board's policy decides zone-zone overlap, but validating all peers against the actual solved frame is necessary to make that promise.

## Proposed scene contract

`WorkspaceScene` owns an identity-stamped workspace document, a map of `ZoneNode`s, and a root node for bare tiles. Every mounted zone has exactly one node, canonical placement, derived header presentation, **creation scope**, and a visual tile membership list. Each project tile has one durable `(ownerProjectId,tileId)` record with a WORLD frame and a known loading state; `ownerProjectId` determines the `canvas.json` writer and remains stable when the zone's creation scope changes. Ambient tiles are owned by the workspace, whether grouped or bare. Views and runtime processes are caches attached to records, with separate lifecycle and budget. A failed project canvas read yields an unresolved node that cannot be treated as empty or covered by a persistence merge.

`spawn` first resolves one target zone and project/Home, constructs a candidate tile/world frame, solves growth and pushes over the complete scene, validates containment and non-overlap, then commits all changed records together. `materialize` replaces only a view/runtime for an existing tile. Drag, resize and tidy use the same full-scene solve and validation; every growth pushes neighbours under Dylan's chosen policy. Membership repair must either choose a containing zone and keep the frame, grow a chosen home zone with a complete push solve, or leave the tile explicitly unassigned; stamping an outside tile as inside is disallowed.

The full-scene invariant should be checked at import/mount and at every geometry commit. On mount, report or quarantine incompatible legacy data and preserve it byte-for-byte until a deliberate repair; a runtime failure should never turn a project canvas into an empty authoritative layer. `CanvasState` can remain a disk DTO during migration, but it must cease being a second on-screen tile model and writer. This is narrower than rewriting the canvas renderer: it changes ownership and commit entry points while preserving the existing view types.
