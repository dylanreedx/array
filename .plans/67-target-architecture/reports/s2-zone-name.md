## Suspect paths (ranked)

1. **Highest confidence — global keyboard shortcuts are not gated against an open zone-rename field, so a hotkey silently discards the in-flight rename instead of committing it.**
   - `installHotkeyMonitor()` (`ContinuumApp.swift:7536`) installs a **local `NSEvent` monitor on `.keyDown`** that runs *before* the responder chain / field editor ever sees the key, and swallows the event (`return nil`) whenever `handleHotkey(event)` returns `true` (`ContinuumApp.swift:7538-7540`).
   - `handleHotkey` (`ContinuumApp.swift:7722+`) has an explicit, deliberate gate for exactly one text editor — the agent inbox — via `inbox.isTextEditorFocusedForGlobalShortcutGate` (`ContinuumApp.swift:~7782-7789`) that withholds reserved shortcuts while that field is focused. **There is no equivalent check anywhere in `handleHotkey`/`ContinuumApp.swift` for `canvasView.qaZoneRenameActiveZoneId`/`renamingZoneId`/`zoneRenameField`** (`grep` for those identifiers in `ContinuumApp.swift` returns nothing).
   - Commit of a zone rename only happens through three routes, all responder-chain-mediated: Enter (`control(_:textView:doCommandBy:)`, `CanvasNSView.swift:12785-12788`), Esc-cancel (same method), or `controlTextDidEndEditing` firing on **blur** (`CanvasNSView.swift:12798-12804`). A key event consumed by the local monitor never reaches the field editor and never generates an end-editing notification, so none of the three commit routes fire.
   - Net effect: if Dylan is mid-edit in the inline zone-rename field and presses a reserved hotkey — most plausibly a **workspace-switch shortcut** (`ContinuumApp.swift:15112/15255/15332/15399` all call `workspaceRuntime?.switchWorkspace(to:)` directly from menu/shortcut handlers, none of which call `canvasView.commitZoneRename()` first) or **Cmd+Q** — the edit is thrown away silently: `applyZoneRename` is never called, `liveZones`/`document` still hold the pre-rename (often the auto-generated default, e.g. "Zone 1") name, and that's exactly what gets persisted/reloaded on the subsequent switch or relaunch. This reproduces **both** halves of the bug report (workspace switch AND quit/reopen) from one mechanism, and explains "often" rather than "always" (only reproduces when a hotkey is pressed while renaming, not on every rename).
   - Witness gap: `--zone-rename-inline-check` (`CanvasNSView.swift:11781`) never simulates a reserved-shortcut keyDown while the field is open; it only exercises mouse-driven commit paths (double-click open, click-away commit, `qaRenameZone` direct call). `AGENTS`'s own inbox gate (`isTextEditorFocusedForGlobalShortcutGate`) is the pattern this is missing.

2. **Second — `WorkspaceRuntime.commitZonePlacement` throws `zoneNotFound` and the caller swallows it with no fallback (`ContinuumApp.swift:14751-14757`).**
   - If a rename lands on a zone that exists in `canvasView.liveZones` (so `canvasView?.zonePlacement(for:)` succeeds) but not yet in `workspaceRuntime.document.zones` — e.g. a very fast create-then-rename race, or any path where a zone is added to Model B without going through `commitCreatedZone`/`commitZonePlacement` first — `persistRenamedZone`'s Branch A is chosen, throws, is logged to stderr, and returns. **No disk write happens, and Branch B (the document-store fallback that would still have persisted it) is never attempted.** The user sees the rename in the UI (Model B was already mutated by `applyZoneRename`) until the next switch/reload silently reverts it because disk never agreed.
   - Lower confidence than #1 because ordinary create-then-rename is not typically fast enough to race the synchronous `persistCreatedGroupZone` commit, but it is a real, silent-failure gap worth closing regardless (no `fputs` message reaches the user, no witness covers it).

3. **Lowest — `setZones`'s documented "layer refresh restored old name" regression class is pinned by a check, but only for the same-session reinstall case (`CanvasNSView.swift:11884`), not for a reinstall sourced from a `WorkspaceDocument` load that raced an unflushed save.** Given every writer found is synchronous (table above), this path currently looks closed, but it is the shape of hazard `setZones` was already bitten by once, so any future change that reintroduces debouncing on the document save (e.g. wiring zone rename through the tile-geometry debounce/`flushCanvasSave` instead of `WorkspaceDocumentSaveController`'s immediate flush) would reopen exactly this class.

## Ordering hazards

- Zone-name persistence itself is **not debounced** — `commitZonePlacement`/`persistWorkspaceDocument` create a fresh `WorkspaceDocumentSaveController` and call `flush(through:)` synchronously every time (`WorkspaceRuntime.swift:1432-1445`). This is unlike tile-geometry saves, which do go through `ZoneRuntimeController`'s 200ms debounce timer (`ZoneRuntimeController.swift:676-735`) and `AutosaveConfig.debounceInterval` (`WorkspaceDocumentSaveController.swift:39-49`).
- `applicationShouldTerminate` (`ContinuumApp.swift:16710-16718`) and `windowShouldClose` (`:16741-16749`) both call `workspaceRuntime?.flushMountedWorkspaceState()` before allowing quit/close, and that call is synchronous and blocking (`.terminateCancel` on failure) — so there **is** an effective `applicationWillTerminate`-adjacent flush gate for anything already committed to `liveZones`/`document`. This closes the classic "debounce didn't fire before quit" hazard for renames that were actually committed.
- The gap is therefore not "was the commit debounced/flushed too late" — it's "was the commit ever made at all" — which is exactly Suspect #1: an uncommitted, in-progress rename is invisible to every flush-before-teardown safeguard because those safeguards only ever look at `liveZones`/`document`, never at the still-open `NSTextField`.

## Existing witnesses that cover renaming

- `CanvasNSView.runZoneRenameInlineSelfCheck()` / `--zone-rename-inline-check` (`CanvasNSView.swift:11781`, wired at `ContinuumApp.swift:2826`): covers double-click-to-open, `selectText` self-commit guard, click-focus-router not stealing the field, click-away commit, empty/whitespace no-op, `setZones` layer-reinstall not reverting an already-committed rename, and Codable round-trip. Does **not** cover: a reserved-shortcut keyDown while the field is open, `switchWorkspace`, or app termination while renaming.
- `docs/VERSIONING.md` 0.4.13 entry documents a related-but-distinct navigation/focus defect fixed for zone jumps stranding keyboard input — same neighborhood (focus/shortcut routing around zones) but not this bug.
- No `--zone-rename-*` or `--workspace-switch-*` check exercises a hotkey fired mid-rename; no check exercises `applicationShouldTerminate`/`windowShouldClose` with an open zone-rename field. This is the missing witness that should go RED before any fix and GREEN after.
