# Array companion catch-up and architecture refactor

- Status: **in progress — Phase 0 authority packet; relay implementation loop remains stopped**
- Owner: Dylan
- Scope: macOS Array, iPhone companion, provider backends, sync/relay, pairing/auth, shared agent content/UI, verification, migration, and release
- Current baseline: desktop Array 0.4.2 (build 8); iPhone Continuum 0.1.0 dogfood client; legacy in-memory/long-poll relay

## Progress

- **2026-08-10 — Phase 0 authority packet started.** This umbrella plan and the prepared ticket-92 relay program are being committed together as the local implementation authority.
- The relay program's `STOP` remains armed. Its implementation loop must not start until the preserved queue-91 P4.6 candidate is resolved and the checkout satisfies the relay runbook's clean-tree/preflight rules.
- Existing desktop command-center, agent-home, context-occupancy, brand, archive, and website work is outside this packet and remains untouched.

## Outcome

Array will have one provider-neutral agent architecture and two first-class clients. A managed agent started through Claude Code, Codex, or pi will produce the same durable semantic transcript and lifecycle stream. The Mac and an authorized iPhone will reduce that stream into the same conversation, status, approval, and command state. A separately installed relay will persist accepted data before broadcasting it, survive UI and relay restarts, and report sleeping or disconnected execution hosts honestly.

The completed product must support this concrete workflow:

1. Dylan starts a managed agent on the Mac using Claude Code, Codex, or pi.
2. The iPhone shows the same agent, live status, transcript blocks, tool activity, context facts, and pending human requests.
3. Dylan can send a prompt or follow-up, answer an approval/input request, stop the agent, or reopen its workspace from the phone when his execution host is online and his device has the capability.
4. Closing the Array window does not stop the relay service. Relay restart does not lose pairings, cursors, transcripts, commands, or push registrations.
5. If the execution Mac sleeps, the phone retains readable history, marks the host offline, and refuses execution commands instead of pretending they were delivered.
6. No provider credential, environment value, private absolute path, raw process handle, or generic shell authority enters the relay.

## Definition of done

- The formal provider backend registry owns execution, availability, auth readiness, model catalogue contribution, capability reporting, resume state, and transcript import for Claude Code, Codex, and pi.
- `AgentSupervisor` selects backends through that registry and no longer contains provider construction switches.
- Provider output normalizes into a versioned semantic agent-document mutation stream used by both live rendering and transcript rehydration.
- The relay persists identity, authorization, workspaces, agents, generations/sequences, transcript mutations, snapshots, commands, receipts, blobs, push registrations, quotas, and backup metadata in SQLite WAL.
- The relay transport is bounded HTTP/WebSocket over a private-network-first deployment, with application-layer credentials, heartbeat, replay cursors, backpressure, and graceful restart.
- The iPhone is split into maintainable feature and infrastructure modules; it is branded Array and is no longer one monolithic `ContinuumApp.swift` implementation.
- Mac and iPhone show the same authorized transcript and command outcomes from snapshot plus tail replay.
- Pairing credentials are server-generated, stored hashed at rest on the relay, stored in Keychain on clients, scoped by workspace capabilities, expiring/revocable, and never carried in URLs or JSON hello bodies.
- CloudKit and the ticket-86 relay remain available only during a measured compatibility window, then are removed from the production default path.
- The full verification matrix is trustworthy: known-red blockers that prevent later legs from executing are fixed or split into non-blocking, independently reported gates.
- Simulator, physical-device, restart, sleep/offline, backup/restore, migration, and rollback acceptance passes are recorded before release.

## Non-goals

- Public multi-tenant SaaS, public signup, organization billing, SCIM, SSO, or a globally replicated control plane.
- Moving provider credentials or raw provider processes into the relay.
- Generic remote shell or arbitrary filesystem browsing from the phone.
- Exactly-once provider execution. Ambiguous post-dispatch failures end in `indeterminate` and require reconciliation or an explicit retry.
- Horizontal relay scaling, Kafka/Redis, distributed consensus, or object storage before the single-node limits are measured and exceeded.
- Migrating an agent process off a sleeping execution host. Another already-awake host may continue only its own agents.
- Rewriting canvas op-log semantics that already converge; the existing spatial `SyncMessage` path remains separate from privileged agent content/control frames.

## Current state and gaps

### What is worth preserving

- `AgentSupervisor` already owns agents independently from tiles and multicasts runtime events.
- `AgentRunning` gives deterministic checks an execution seam.
- `PiAgentRunner`, `ClaudeAgentRunner`, and `CodexAgentRunner` isolate provider process management and translators.
- `AgentRuntimeEvent` gives status/activity consumers a provider-neutral live vocabulary.
- `ManagedTranscriptRehydrator` proves provider session files can reconstruct local display history without republishing sensitive bodies.
- `ContinuumRevivedAgentContent` and `ContinuumRevivedAgentUI` already enforce one-way shared-module boundaries.
- `SyncTransport`, `SyncMessageDemux`, spatial op-log/snapshots, activity projection, approval response, pairing, and freshness semantics are working foundations.
- The phone already has Agents, Canvas, Approvals, Settings, relay/CloudKit selection, pairing, stale/offline presentation, APNs categories, and operator-gated canvas mutations.

### What must change

- `AgentRunning` covers only run/stop/observations. Backend availability, auth, catalogue, routing, resume state, transcript import, and capabilities remain spread across static types and switches.
- `AgentSupervisor.productionRunner(for:)` knows every provider and must change for each new backend.
- Live transcript projection, disk rehydration, and sanitized companion activity are adjacent representations without one durable semantic mutation contract.
- The current relay uses process-memory authority, a lifetime-local sequence, raw HTTP long-poll, token registration from client-supplied scope bits, and an in-memory ring. It is a dogfood bridge, not a durable control service.
- The current `SyncMessage` vocabulary intentionally excludes full transcript/control content. Expanding it would mix spatial replication with privileged interactive operations and weaken authorization review.
- The entire phone state/lifecycle/navigation implementation is concentrated in `ios/Continuum/Sources/ContinuumApp.swift`.
- The phone still presents the Continuum 0.1.0 identity while the desktop product is Array.
- Full-matrix execution is obstructed by known-red legs; later checks can remain unexecuted without an independent result.
- The prepared small-team relay design and scripts are not tracked, so there is no committed implementation authority yet.

## Hard-to-reverse decisions

### 1. Durable transcript contract

The canonical relayed transcript is a versioned stream of semantic `AgentDocumentMutation` values, not raw provider JSON, AppKit/SwiftUI view models, or lossy activity summaries. Mutations use opaque workspace, environment, agent, generation, turn, item, and mutation IDs. Snapshot plus tail must reduce to the same document as complete replay.

Provider adapters may retain provider-specific cursor/session facts locally, but the transcript mutation schema must not encode Claude/Codex/pi-specific wire events. Unknown semantic block kinds are preserved as bounded opaque native-rendered blocks; they are never rendered as arbitrary HTML.

### 2. Two information planes

- **Class A — notification projection:** categories, safe configured titles, lifecycle, and opaque IDs. It can feed APNs and lock-screen UI; it contains no prompt, response, tool body, path, or credential.
- **Class B — authenticated interactive content:** transcript mutations, rendered tool/diff content, prompts, answers, and explicit agent commands. It requires device/environment identity, workspace membership, operation capability, limits, and audit metadata.
- **Class C — host-only runtime/secrets:** provider credentials, environment values, private absolute paths, process handles, signing material, generic shell commands, and unrelated files. It never enters RelayProtocol, relay persistence, logs, metrics, backups, or APNs.

The existing taint scanner remains defense in depth for Class A and compatibility messages. It is not authorization for Class B.

### 3. Relay identity and credentials

The relay creates one-use pairing invitations and returns 256-bit opaque credentials exactly once. It stores only credential hashes and metadata. A human device and an execution environment are different principal kinds with non-interchangeable credentials. Workspace capabilities are server-derived and stored; clients never submit raw scope bits as authority.

Initial capabilities:

- `transcript.read`
- `tool.read`
- `prompt.send`
- `agent.steer`
- `approval.respond`
- `agent.stop`
- `agent.create`
- `canvas.read`
- `canvas.edit`
- `device.manage`
- `workspace.admin`
- `relay.admin`
- execution-host publish/consume capabilities scoped to configured workspaces

### 4. Command delivery

Every command has a device-scoped idempotency key and durable state:

```text
received → authorized → committed → forwarded → hostAccepted → completed
                                      ├────────→ refused
                                      ├────────→ expired
                                      └────────→ indeterminate
```

The relay persists a command before forwarding it. The host revalidates the command against its local agent/project/model catalogue and may refuse it. A disconnect after forwarding but before acknowledgement is `indeterminate`; the relay never blindly redispatches provider execution.

### 5. Migration strategy

Migration is additive and reversible:

1. Build new protocol/core/client modules without changing the production transport selection.
2. Dual-publish sanitized legacy activity plus new semantic frames from the Mac in dogfood builds.
3. Make the iPhone prefer the new relay while retaining a one-release compatibility fallback.
4. Compare reducers and cursors in shadow mode; do not enable phone commands until read parity is proven.
5. Enable commands one capability at a time.
6. Remove token-registration and scope authority from the legacy relay before public/private-network exposure.
7. Retire the long-poll relay and CloudKit production default only after physical-device, restart, backup/restore, and rollback acceptance.

No persisted provider session, `AgentRecord`, canvas op-log, pairing record, or phone cache is destructively rewritten without a versioned decoder and an exported rollback fixture.

## Proposed data model

The durable relay owns these tables or equivalent repositories:

- `relay_metadata`: schema version, relay ID/fingerprint, creation and migration facts.
- `workspaces`: stable opaque workspace identity and safe display metadata.
- `devices`: principal identity, credential hash, expiry, revocation, last-used metadata.
- `workspace_memberships`: canonical capabilities by device/workspace.
- `pairing_grants`: one-use invitation hash, requested role, expiry, consumed fact.
- `environments`: execution-host principal, credential hash, lease, safe catalog revision.
- `agents`: workspace/environment ownership, generation, latest sequence, lifecycle.
- `agent_events`: unique `(agent_id, generation, sequence)` plus stable host event identity and bounded mutation payload.
- `agent_snapshots`: semantic document snapshot through a committed sequence.
- `commands`: unique `(device_id, idempotency_key)`, payload kind, state, timestamps, refusal/indeterminate metadata.
- `provider_requests`: outstanding approval/input request and durable resolution.
- `blobs`: content hash, size, media semantics, storage path, quota/refcount facts.
- `push_registrations`: encrypted APNs token material and device/category metadata.
- `rate_limit_buckets`, `quota_usage`, `backup_metadata`, and migration ledger.

Persistence invariants:

- Foreign keys on; WAL/busy/synchronous policy explicit and measured.
- Authorization, generation/sequence assignment, event insert, and quota reservation occur atomically where they belong to one accepted action.
- Persist before broadcast.
- Identical host retries return the existing committed event; conflicting bytes for one identity are rejected.
- Snapshot plus tail equals complete replay.
- Blob paths derive only from verified content hashes below a relay-owned root.
- Backups contain a consistent database and referenced-blob manifest and are encrypted before leaving the host.

## Provider backend contract

Add a public/core protocol and registry with a narrow host-owned process adapter:

```swift
public protocol ManagedAgentBackend: Sendable {
    var id: ManagedAgentBackendID { get }
    var capabilities: ManagedAgentBackendCapabilities { get }

    func availability() async -> BackendAvailability
    func authenticationReadiness() async -> BackendAuthenticationReadiness
    func catalogue() async -> BackendModelCatalogue
    func supports(modelID: String) -> Bool
    func makeRunner(for record: AgentRecord) throws -> any AgentRunning
    func resumeReference(for record: AgentRecord) -> BackendResumeReference
    func transcriptSource(for record: AgentRecord) -> BackendTranscriptSource?
}
```

`ManagedAgentBackendRegistry` owns ordered backends, explicit user preference, capability-aware routing, catalogue union/deduplication, availability caching, and human-readable failure reasons. The registry must never silently route an explicitly selected unavailable Claude/Codex harness to pi. It returns a structured refusal pointing to Environment Setup. The default “automatic” policy may prefer native subscription CLIs by provider and fall back to pi only when the user selected automatic/pi-all-providers behavior.

The initial adapters wrap existing code rather than rewrite it:

- Claude: `ClaudeCLIBackend`, `ClaudeAgentRunner`, `ClaudeEventTranslator`, `ClaudeSessionTranscriptReader`.
- Codex: `CodexCLIBackend`, `CodexAgentRunner`, `CodexEventTranslator`, stored `codexThreadId`, session transcript reader added if the semantic store cannot satisfy old history.
- pi: `PiAgentRunner`, `PiEventTranslator`, `PiSessionTranscriptReader`, live catalogue/auth probe.

Once registry routing is live, remove provider construction switches and duplicate onboarding/model-picker policy. Keep provider CLI auth ownership unchanged.

## Risks and controls

- **Schema lock-in:** freeze only provider-neutral semantics and preserve unknown blocks; require compatibility fixtures before changing public IDs or payloads.
- **Sensitive transcript exposure:** separate information classes, authorize every operation, keep credentials host-only, encrypt transport/backups, limit payloads, and scan all observability surfaces.
- **Duplicate or ambiguous execution:** persist commands first, use device idempotency keys, target agent generation, and expose `indeterminate` without blind retry.
- **Half-migrated clients:** dual-publish, shadow-compare, negotiate protocol capabilities, retain a bounded compatibility fallback, and gate commands after read parity.
- **Monolith moved rather than removed:** feature modules own state/actions; AppCoordinator only composes dependencies and navigation.
- **Provider abstraction overgrowth:** wrap existing adapters first; the protocol contains demonstrated cross-provider capabilities, not speculative provider APIs.
- **Relay operational burden:** one-node/private-network-first deployment, SQLite/local blobs, explicit limits, doctor/backup/restore tooling, and no public bind by default.
- **Untrustworthy verification:** Phase 0 precedes refactoring and makes every leg execute independently.
- **Identity/App Store breakage:** change display/project identity separately from the bundle identifier and verify ownership/provisioning before any bundle migration.

## Explicit defaults for approval

Unless Dylan changes them during review, implementation proceeds with these decisions:

1. **Deployment:** private-network-first single relay on an existing awake Mac/Linux host; a low-cost VPS is optional after local acceptance.
2. **Storage:** SQLite WAL plus relay-owned content-addressed local blobs.
3. **Transport:** SwiftNIO HTTP/WebSocket; loopback default; TLS at an explicitly configured private-network/reverse-proxy boundary plus application credentials.
4. **Transcript:** authorized full semantic transcript and tool/diff content on the relay; provider credentials, environment values, private absolute paths, and generic shell authority remain host-only.
5. **Product identity:** rename the iPhone product/project/display surface to Array; keep the current bundle identifier until provisioning/App Store ownership is verified.
6. **First command slice:** approval/input response, then prompt/follow-up, then stop, then restricted create-agent.
7. **Legacy transports:** dual-run for migration, one explicit rollback release, then remove them from the production default path.
8. **Provider routing:** explicit Claude/Codex selection never silently falls back to pi; automatic/pi-all-providers mode may use documented fallback.

## Approval boundary

Approval of this plan authorizes ticketing and implementation in the ordered phases. It does not authorize destructive migration of existing companion/agent data, public internet exposure of the relay, changing the iOS bundle identifier, uploading an iPhone build, releasing artifacts, or retiring compatibility transports without their named acceptance gates.
