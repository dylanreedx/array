# Restore tmux shell-tile isolation

Status: **implemented; real-tmux, full-matrix, and visual dogfood verification
remain supervised because this sandbox cannot create an isolated tmux socket**.

Branch: `array/tmux-shell-isolation`

Base and current checkout commit: `0a0684a7031b2665eadb1a09fa15ecb625c47292`

## Objective

Repair the tmux shell-tile mirroring regression without abandoning the shared
project-session architecture. Every terminal that uses a shared project or
workspace session must attach through a stable per-tile grouped view session.
Each view keeps its own selected-window state, survives a live-target restart,
and repins to a replacement window when its persisted pane dies.

Done means:

1. The corrected production witness is captured RED before implementation and
   GREEN after.
2. Two fresh project terminals launch through distinct `array-view-<tileId>`
   sessions pinned to distinct targets.
3. Live restart reuses the pane, dead restart replaces it exactly once, and both
   preserve the stable view-session identity.
4. Shared ambient terminals are isolated when `ambientPerWorkspace=true`; the
   existing per-tile fallback remains when it is false.
5. Create, select, query, attach, recovery, and cleanup all address the same
   local or remote tmux owner.
6. Tile deletion and failed-spawn rollback remove only tile-owned resources;
   sibling views/windows and the base session survive.
7. The production-generated real-tmux I2 check, app-level no-mirror check,
   Ghostty live integration, and full matrix all report the repaired behavior.
8. Array Dev passes visual dogfood across app relaunch using only
   `scripts/dev-app.sh` and `~/array-scratch`.
9. The verified, scoped change is committed on the requested branch under
   Dylan's configured identity.

<Callout id="root-cause" tone="decision">

**Root cause and repair:** production creates distinct windows in one shared
base session but launches every Ghostty surface with `tmux attach-session -t
%pane`. A pane target chooses the initial window; it does not create an
independent selected-window pointer. The selected window belongs to the shared
session, so clients converge and mirror. Keep the shared base, but launch every
shared tile through `array-view-<tileId>` using one production builder:
`new-session -t <base> -s <view> -A ; select-window -t <capturedTarget>`.
The `";"` is one literal argv element, and the view attach never includes the
shell or agent inner command.

</Callout>

## Repository evidence

The requested checkout is clean and exactly on the requested base. The tree
already contains the architectural ingredients, but they are disconnected:

- `TmuxSession.viewSessionName` and `killViewSessionCommand` use stable
  `array-view-<tileId>` identities.
- `groupedViewSessionArguments` and `selectWindowArguments` prove grouped
  sessions work, but no production-shaped `LaunchProfile` builder composes
  them.
- `TileSpawner.tmuxWrappedProfileIfAvailable` creates distinct project and
  opted-in workspace windows, then returns `attachWindowProfile` for both fresh
  creation and live-target restart.
- Dead-target restart correctly creates a replacement window, but returns the
  same broken direct attach.
- The production persistence check explicitly expects the broken direct attach
  and therefore protects the regression.
- The real-tmux I2 block manually creates and selects grouped sessions rather
  than executing production-generated argv.
- Deliberate deletion already kills the captured window and then the stable
  view session, even though production never creates that view.
- Rollback after descriptor persistence failure kills the new window, but does
  not yet model whether a view was created or reused.
- `TmuxSession.wrap` can SSH-wrap a Ghostty launch, while `TileSpawner`, app
  deletion, `ZoneRuntimeController` observer/reaper, and lazy recovery construct
  local `ProcessTmuxControl`. A remote launch can therefore silently split from
  local creation, querying, and cleanup.

## Settled implementation decisions

### Shared ambient remains supported

When `ambientPerWorkspace=true`, use `array-ws-<workspaceId>` as the shared
base and `array-view-<tileId>` as each terminal's isolated view. When the option
is false, keep the existing isolated `array-<tileId>` fallback. This closes the
same mirroring defect without silently disabling an existing option.

### One builder owns grouped-view launch construction

Add one production-shaped Core builder with explicit inputs:

- original `LaunchProfile`;
- stable tile ID;
- explicit base session name;
- captured pane/window target;
- tmux path;
- `RemoteReach` and defaults used for SSH construction.

It preserves cwd and title, emits the literal `";"` argv token, and contains no
inner command. Project and workspace call the same builder with different base
names.

### One reach-aware control path owns daemon operations

Localhost executes tmux directly. SSH-forward and Tailscale execute the same
tmux argv remotely through the existing hardened SSH options and token quoting.
Tunnel remains explicitly unsupported. A caller must not calculate remote reach
for the Ghostty launch and then create a path-only local `ProcessTmuxControl`.

### Rollback is attempt-aware

The spawn path records which window and view resources this attempt created or
reused. If persistence fails, stop and remove the just-installed Ghostty surface
before compensating, so it cannot create a late view after cleanup. Remove only
newly created resources. Never kill a reused live window/view, a sibling, or the
shared base session generically.

### Machine and visual proofs remain distinct

The new app no-mirror check deterministically drives production TileSpawner
fresh and restart paths and executes their generated profiles against real tmux.
The existing live integration remains the Ghostty surface proof. Final visual
dogfood remains supervised because terminal rendering and focus behavior need
human observation.

## Implementation sequence

### 1. Correct the production witness and capture RED

Edit only the shared assertions in
`TileSpawner.runTerminalTmuxPersistenceSelfCheck` first:

- require one shared base project session;
- require distinct persisted pane targets;
- derive and require one stable, distinct `array-view-<tileId>` per tile;
- require `new-session -t <base> -s <view> -A`, literal `";"`, and
  `select-window -t <target>` in order;
- require that the original shell command is absent;
- explicitly reject `attach-session -t %pane` as the complete launch argv;
- apply the same contract to opted-in shared ambient descriptors.

Rebuild the app before running the check so a stale binary cannot hide RED:

### 2. Add grouped-view and reach-aware Core construction

In `Sources/ContinuumRevivedCore/TmuxSession.swift`:

1. Add a production `LaunchProfile` builder for the entire grouped-view attach.
2. Use an explicit `baseSessionName` so project and workspace share the code.
3. Preserve the profile cwd/title.
4. Emit exactly one literal `";"` argument.
5. Do not call `shouldPassInnerCommand` or append the original command/args.
6. Extract or reuse one pure reach-aware command constructor so local and
   SSH/Tailscale invocation semantics cannot drift between Ghostty launch and
   process control.

In `ProcessTmuxControl.swift`, retain the resolved reach/defaults or an
equivalent immutable owner descriptor. Route every protocol operation through
the common constructor. Extend `InMemoryTmuxControl` only where checks need to
represent grouped-view existence, selection, or forced failures; do not keep a
second manually assembled ideal topology in tests.

Add Core assertions for:

- stable view naming and distinction from per-tile/base names;
- exact project and workspace base target;
- exact selected pane target;
- literal `";"`, never `"\\;"`;
- no shell/agent inner command for shell and non-shell profiles;
- cwd/title preservation;
- local tmux command construction;
- SSH-forward and Tailscale construction with configured host, port, config,
  keepalive, quoting, and remote tmux path;
- explicit tunnel refusal rather than local fallback.

### 3. Wire fresh spawn and both restart branches

Refactor `TileSpawner.tmuxWrappedProfileIfAvailable` to resolve one base session
name from `TerminalSessionTarget` and obtain a control for the same reach used
by the returned launch profile.

Fresh shared spawn:

1. Create a new window in the base session, retaining the current first-window
   fallback to base-session creation.
2. Validate and persist the captured pane target.
3. Return the grouped-view profile for the stable tile view.

Live-target restart:

1. Probe the persisted target through the correct owner.
2. Reuse the same target without creating a window.
3. Recreate/attach the same stable view and explicitly select the target again.

Dead-target restart:

1. Detect the dead pane through the correct owner.
2. Create exactly one replacement window, creating the base only if absent.
3. Persist the new target.
4. Repin the same stable view-session name.

Nil targets and non-shared ambient terminals remain on `TmuxSession.wrap`. View
attach never reruns the inner command; that command already started when
`newSession` or `newWindow` created the content.

### 4. Make rollback and lifecycle ownership exact

Return attempt metadata from the shared spawn preparation: target, base/view
identity, whether the target was reused, and which resources were newly
created. If descriptor/canvas persistence fails:

1. terminate/detach the failed runtime and remove its installed tile surface;
2. kill a newly created view if it exists;
3. kill only the newly created window;
4. leave reused windows/views, siblings, and the base untouched.

In `ContinuumApp.swift`, resolve deliberate deletion through the owning
project/controller reach. Kill the captured window first and then
`array-view-<tileId>`. Preserve the nil-target legacy per-tile session cleanup,
but run it against the same owner. Keep app/window teardown and project release
detach-only.

Audit `ZoneRuntimeController` operations addressing the same session or panes:

- session observer query;
- reaper construction;
- focus-driven lazy recovery and replacement-window creation.

Each must receive the same reach-aware control. Do not broaden this work into
tunnel transport or redesign the observer/reaper.

## Risks and guardrails

- **Separator semantics:** Swift passes a literal `";"` argv token. The
  shell-escaped `"\\;"` is incorrect here.
- **Late view creation during rollback:** stop/remove the failed Ghostty surface
  before compensating tmux resources.
- **Last-window behavior:** killing a failed attempt's only new window may let
  tmux reap a base the attempt created; never issue a generic base kill.
- **Remote split-brain:** carry reach into both launch and control construction.
  A path-only factory is not sufficient.
- **Observer behavior:** reads target panes directly and must not call
  `select-window`.
- **Matrix visibility:** the new leg must be literal, inventory-pinned, and
  visible in the final report.
- **Workspace safety:** keep all dogfood in Array Dev and `~/array-scratch`.

## Open questions

There are no design questions requiring a choice before implementation. The
base/view topology, shared-ambient rule, literal separator, lifecycle behavior,
remote-owner invariant, verification gates, dogfood boundary, and commit
requirements are fixed by the task and repository evidence.
